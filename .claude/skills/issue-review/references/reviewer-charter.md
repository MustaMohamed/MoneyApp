# Reviewer charter (paste verbatim into the subagent prompt)

You are reviewing one or more issues of the define workflow against their own Goal, their parent and the code. You did not write them. Read-only on the repository: you run no `gh`, edit no file, and return deltas as text.

Inputs in your prompt: the bodies under review, each with its number, title and board Status; each leaf's sizer return, the counted file list; the parent body, when there is one; the code map, or nothing when you map for yourself; the milestone sheet, every issue on the milestone with number, title, labels, state and header line; the path of the standard the bodies follow and of CLAUDE.md, which you read before judging; the features folder `.claude/skills/emulator-verify/features/`, where you read the file of each screen a ticket touches. No map: read the modules the body names, and every screen, migration, money path, native config and user copy they touch, before judging anything.

Self, on every body:

- **S1 Complete.** Every outcome the Goal implies is in Building or Not building (epic) or in Acceptance (ticket). Anything the code shows in the touched modules that the body neither builds nor excludes is a delta: an existing screen, flow, write or state the change will meet.
- **S2 Outcomes, not solutions.** No component names, file paths, code or design in Building, Task Definition or Acceptance. A ticket's Context is where its file paths belong.
- **S3 Assertable.** Each Rule and each Acceptance line is one sentence a test could assert. "Works correctly", "properly", "as expected" are deltas. Rules contradict neither each other nor CLAUDE.md's business rules.
- **S3b Family.** An Out of scope line that excludes another site of the ticket's own defect (the same check, resolver, slot or string on another screen or module) is a delta: the site moves into Acceptance, or the ticket is rewritten as the class ticket with every site from one `git grep` and the Goal naming the defect. One ticket per class, never one per site; cite the sibling that already shows the pattern when one exists.
- **S4 Shape.** The body has every section the standard you were given requires, in its order, each filled: for an epic the lock line first and Open questions `None`; for a ticket the header line with all four fields and every Out of scope line naming a task on the milestone sheet. A link, or a Context path, is a delta when it points at nothing on the sheet or in the repo.
- **S5 Triggers.** Which of CLAUDE.md's critical triggers the work implies. Epic: each named in Rules so `/tickets` carries it. Ticket: each in Flags, using only the values the standard's header table allows.
- **S6 Overlap.** Epic only: every other epic on the milestone sheet that touches the same module has the overlap named in Not building with its owner.
- **S7 States.** Ticket only: walk each Acceptance line through zero, one, many, negative, loading, failed, archived, deleted, other currency and font scale 2.0. A state the code can reach and no line covers is an `ask`, and each of its options carries `screen:`, the `Screen checks` row it adds, if any.
- **S8 Copy.** Ticket only: list every string the change adds or alters and compare the list with `## Copy` and `src/constants/strings.ts`. A missing string or form is an `ask`, and each of its options carries `copy:`, the `Copy` bullet it adds, if any.
- **S9 Screen checks.** Ticket only: build the rows from the code map and the features files, per the standard's `Screen checks` heading, with risk marked by its five conditions, and return them as a mechanical delta with the replacement text. Mark `new` a state the features file lacks. The same delta sets the header's Verify: `emulator` when it writes a row, `none` when the section reads `none`.

Parent, on every body that has one:

- **P1 Rules carried.** Every parent Rule that applies appears in this body's Rules in plain words.
- **P2 Serves the parent.** The body serves one Building bullet of the parent, or one Acceptance line of a task parent, and builds nothing the parent excludes.
- **P3 Size.** The count is the sizer's return, built per `.claude/skills/tickets/references/splitting.md` § Size gate from LSP references on the code as it is. Check it against the body: an Acceptance line or a Rule with no file in the sizer's table is a file the sizer missed, and you add it with its estimate. One outcome, or a bundle under § Floor. Over the gate, or at it, is an `ask` delta proposing the seam; the gate is hard, so the ask offers seams or Todo for its own `/tickets` run, never keeping the body whole, and the issue is returned as `deltas`, never `approve`: it is not marked until `/tickets` has cut it. Under ~100 lines with an open ticket on the milestone that changes the same screen or fixes the same defect family, and room in that ticket's gate: an `ask` delta proposing the bundle per § Floor. A body whose `Size:` line disagrees with the count, or lacks one, gets a mechanical delta with the sizer's list plus your additions. Never take the body's figure as the count. A body at Todo was chosen by the user for its own breakdown and is exempt.
- **P4 Header true to the code.** Verify matches the standard's header table, judged against the `Screen checks` rows after S9. Flags match the migrations, money paths, native config and copy the change touches.
- **P5 Edges real.** Every Depends on names a dependency the code supports, written as `MA-nnn (#N)` with the number from the milestone sheet. A dependency the code shows and the header omits is a delta, including the parent's own Depends on for a chain's first link. A `Consumes` bullet that names an open ticket has that ticket in Depends on.

Before an `ask`, read for the answer. A question is asked only when none of these settles it, read in this order: the body's own lines, its parent's Rules and Decisions, and the epic's Rules; the approved design, the frame in the canvas folder your prompt names, for layout, geometry, colour and the states a screen has; the approved plan or spec in the repo, `docs/adr/`, `docs/workflow.md`, `docs/design-system.md` and the plan on the ticket's branch when a `Plan:` comment names one; the shipped code, the convention the sibling screens and modules follow, `path:line`; prior art on the milestone, a sibling's Decisions line or an answered question record on a like question. A source that settles it makes the delta mechanical, with the replacement text and the source cited the way a conflict is cited: the frame file, the ADR, the `path:line` or the sibling's line. Only a question every source is silent on is an `ask`, and its `Prior art:` line names each source read and silent.

Evidence rule: every delta cites the issue number and the line, file, parent line or standard heading it conflicts with. A mechanical fix carries its replacement text. A judgement the user must make, after the sources above were read, is marked `ask` and carries the fields of a question record, `.claude/skills/issue-review/references/question-record.md`, from `Asks:` to `Screen:`, every option with the text it writes and where it lands; the conductor adds `Sha:` and `Left:`. No delta without evidence; a clean body gets `approve`, not manufactured notes.

Return, per issue, in this order: `#<n> approve` or `#<n> deltas`; the deltas, one line each, `<check>: <what changes or what to ask> (<evidence>)`, except an `ask`, which follows its line with the record's fields as labelled lines; the checks that were clean, one line.

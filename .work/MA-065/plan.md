## Risks
- A fresh list mount from the transaction-detail entry paints the store's `loadError` as `ErrorState`: the list hook loads nothing on mount (`accounts_list.hook.ts:65-68` resets the archived card only), so Acceptance 2's failed-load state holds there too.
- `loadAccounts` sets `loadError` only when its request id is still current (`account.store.ts:71`); a reload started elsewhere during the restore's reload can win the stamp, and the detail then reads `loadError` false and takes the in-place path against a list that did reload. That is the store's existing generation guard, not a defect this ticket adds.
- Step 3's test relies on `attachMockSelectorStore` re-evaluating its getter per call; if the implementer flips `loadError` by mutating a captured object instead, the assertion still holds, but reading the getter contract first avoids a false failure.
- The per-entry landing depends on expo-router 57.0.21's vendored `POP_TO` (pop if present, replace current if absent); an expo-router bump that changes it moves the transaction-detail landing, and no unit test would catch it.
- Amended 2026-09-15 (PR #484 battery, human ruling): step 3's `router.back()` became `router.dismissTo('/accounts')`, because transaction detail's transfer card also pushes the archived detail and `back()` landed there; the Risks line that assumed a single entry was replaced.

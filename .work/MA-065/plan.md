## Risks
- The archived detail is pushed from the archived list row (MA-056), so `router.back()` lands on the accounts list; if a later ticket opens it from elsewhere, "returns to the list" becomes "returns to the previous screen", the same as archive, and Acceptance's wording should follow.
- `loadAccounts` sets `loadError` only when its request id is still current (`account.store.ts:71`); a reload started elsewhere during the restore's reload can win the stamp, and the detail then reads `loadError` false and takes the in-place path against a list that did reload. That is the store's existing generation guard, not a defect this ticket adds.
- Step 3's test relies on `attachMockSelectorStore` re-evaluating its getter per call; if the implementer flips `loadError` by mutating a captured object instead, the assertion still holds, but reading the getter contract first avoids a false failure.

## Self-assessment
Step 3 is the least certain. The behaviour is fixed by Acceptance (pop with the toast, no line, no spinner), but where the `loadError` read sits relative to the slot reset changes what the screen paints during the pop: resetting the slot first drops the view to `loading` for a frame, which is the blank-title state the ticket describes as the defect. The plan therefore reads `loadError` before the reset and skips the reset on that path; if the implementer finds the unmount effect does not fire on `router.back()` in some navigator state, the slot would keep a `ready` row for an id that is now active, and the existing `resolveViewState` order (active list wins, `helpers.ts:19`) is the only thing preventing a stale archived paint on the next visit.

# MA-044 — Key the commitment detail screen-data slot by its owner
base: 4e874579 · verify: none · flags: none · expected diff: ~140 lines outside tests

Shape decision: the data slot (`allPayments`) moves to a new `detail.store.ts`; `viewState` and `skipConfirmVisible` stay in `detail.state.ts`. That is the split `.claude/rules/state.md` names and the layout the transaction detail already has (`detail.store.ts` data, `detail.state.ts` UI). Both stores hold `entries: Record<string, Entry>` keyed by a per-mount `useId()` owner, as `src/modules/transactions/screens/transactions/detail/detail.store.ts:14-45` does. No shared helper: `withEntry` is copied per file, so the transaction detail's files and tests are untouched.

## Risks
- `useId()` yields distinct ids across separate `renderHook` roots today (the transaction hook test at `detail_hook.test.ts:430` depends on it); a React upgrade that resets the counter per root would collide the two copies in tests only.
- The real `useShallow` over a mocked `useCommitmentStore` selector must return stable references: `commitmentsState` and `paymentsState` are reassigned, never mutated, so the shallow compare holds; a test that mutates them in place will loop.
- The `useLocalSearchParams` context wrapper is new test infrastructure; if it proves awkward, the same-commitment cases still cover release isolation and the distinct-commitment case can use `mockResolvedValueOnce` per mount order.
- `oxlint` `react-hooks/exhaustive-deps` on the load effect: the disable comment at `detail.hook.ts:129` must survive the dep-list edit or lint goes red.
- Amended after review: step 2's `setSkipConfirmVisible(true)` case now writes two owners and raises on one, because a one-owner case cannot tell a keyed write from one that replaces `entries` wholesale.

## Self-assessment
Step 3's test rewrite is the least certain. Moving the hook test from a fully mocked `detail.state` module with a `useShallow` passthrough to real keyed stores and the real `useShallow` changes the test's whole footing at once, and the per-copy `useLocalSearchParams` wrapper has no precedent in `__tests__/` (every existing mock returns one module-level params object). The transaction hook test proves the real-store-plus-mocked-domain-store combination works, so the risk is in the params wrapper, and the fallback of mounting two copies on the same payment id with per-call repository responses covers the acceptance lines without it.

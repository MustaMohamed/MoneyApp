## Self-assessment
Step 5 is the one I trust least. The payment move keys on the commitments that still name the deleted account, so it must run before the commitment move, and the whole thing rides MA-038's transaction with the replacement check inside it; the order is stated, but a reviewer or implementer who reorders the two moves for readability silently moves nothing, and the only thing that catches it is the step 5 test asserting `pay-2` names `SURVIVOR`. The rollback case depends on spying `setAccountDeleted` through the module object the way the existing suite spies `clearCommitmentAccount`; if the repository imports it in a form the spy cannot intercept, the test needs a different failure injection, not a different assertion.

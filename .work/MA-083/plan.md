# MA-083 — List: the lifted row scrolls the list from its edge zones
base: cd982cf00b4731ef20c960889cbcac67ecd3f46c · verify: emulator · flags: none · expected diff: ~160 lines

Shape of the change. The lift gesture (`useLiftGesture`) keeps writing the finger; a reanimated frame callback in `useAccountsListDragAnim` reads the finger's position against the scroll viewport, scrolls the `ScreenScroll` from the UI thread with `scrollTo`, and folds the scroll distance into the drag's translation so the slot, the copy and the drop all keep working in the card's own coordinates. Two pure worklets in `accounts_list.reorder.ts` carry the geometry, so the zone and the rate are unit-tested and the emulator walk is one state.

Coordinate contract, used by every step:
- `translationY` (existing) stays the copy's offset from its rest cell, in card coordinates. It becomes finger translation plus scroll distance since the lift: `fingerTranslationY + (edgeScrollOffset - liftScrollOffset)`. `liftedStyle`, `resolveDropIndex`, `useRowShiftStyle` and the `onFinalize` parking keep their current reads of it unchanged.
- `scrollOffset` is the live content offset from `useScrollOffset(scrollRef)`. `edgeScrollOffset` is the offset the frame callback last requested; it equals `scrollOffset` whenever no edge scroll is running (resynced every frame the rate is 0). The callback steps from its own requested value, never from the live one, so scroll-event latency cannot halve the rate or make it stutter.
- The finger's position in the viewport is `fingerAbsoluteY - viewportTop`, both window coordinates: `absoluteY` from the pan event, `viewportTop` and `viewportHeight` from one `measure(scrollRef)` on the first frame of each lift.
- The card's extent in content coordinates comes from a layout-only `View` the screen wraps around `ListCard`: `firstRowTop = y`, `lastRowBottom = y + height`.

### 2. The rate and the clamped next offset are pure worklets
- File: `src/modules/accounts/screens/accounts/list/accounts_list.reorder.ts`
- Change: two exported `'worklet'` functions beside `resolveDropIndex`.
  `resolveEdgeScrollRate(input: { fingerY: number; viewportHeight: number; zoneHeight: number; maxRate: number }): number`, signed px per second: 0 outside both zones, or when `viewportHeight <= 0`, `zoneHeight <= 0` or `maxRate <= 0`; in the top zone (`fingerY < zoneHeight`) `-maxRate * min(1, (zoneHeight - fingerY) / zoneHeight)`, so a finger past the viewport's top edge (negative `fingerY`) runs at `-maxRate`; in the bottom zone (`fingerY > viewportHeight - zoneHeight`) the mirror, positive; when the zones overlap (`viewportHeight < 2 * zoneHeight`) the nearer edge wins, `fingerY < viewportHeight / 2` is top.
  `resolveEdgeScrollOffset(input: { offset: number; step: number; firstRowTop: number; lastRowBottom: number; viewportHeight: number }): number`: `step < 0` returns `max(offset + step, min(offset, firstRowTop))`, so the list scrolls up until the first row is fully on screen and never scrolls up further once it is; `step > 0` returns `min(offset + step, max(offset, lastRowBottom - viewportHeight))`, the mirror for the last row; `step === 0` returns `offset`.
- Test: `first` · `__tests__/screens/accounts/accounts_list.reorder.test.ts`, two describes. Rate: zero mid-viewport; zero at the zone's inner edge (`fingerY === zoneHeight`, and `viewportHeight - zoneHeight`); half rate half-way into each zone; full rate at `fingerY 0` and at `viewportHeight`; full rate past both edges (`fingerY -20`, `viewportHeight + 20`); the sign per zone; zero for a zero viewport; nearer edge wins on an overlapping viewport. Offset: a step up short of the first row lands `offset + step`; a step up past it lands on `firstRowTop`; an offset already above `firstRowTop` (the rail and header on screen) does not move up or down; the three mirrors for the last row with `lastRowBottom - viewportHeight`; a zero step returns the offset; a last row shorter than the viewport (`lastRowBottom < viewportHeight`) never scrolls down past the current offset.

## Risks
- `measure()` and the pan's `absoluteY` may disagree by the status bar height on Android if one is window-relative and the other screen-relative; the zone would sit that far off. Device QA sees it; if it shows, the fix is measuring `viewportTop` from the pan's `absoluteY - y` on `onStart` instead.
- The frame callback keeps running every frame of a lift even mid-viewport (a shared-value read and an early return). If a profiler shows it matters, gate `setActive` on `isHolding` through `scheduleOnRN`.
- `useScrollOffset` on a plain `ScrollView`: the event registration is by tag, not by `Animated.ScrollView`, but a silent no-op would leave `scrollOffset` at 0 and the copy pinned to its lift position after a scroll. The anim test cannot see this; the emulator shot can (the copy no longer under the finger's row).
- `useFrameCallback` re-registers whenever the callback identity changes; `count` in its deps means each reload re-registers once. Harmless, noted so no one "fixes" it into a stale closure.
- Amended, round 2: the Screens line for `grip on every active row` counts on-screen grips, not the twelve seeded, since the recipe's proof counts visible rows.
- Amended, round 1: steps 4 and 5 gained `hasScroll` so `useScrollOffset` takes `null` on the error and no-accounts states, where no `ScreenScroll` mounts and an attached ref would warn once per mount.
- A twelve-account seed pushed onto the shared emulator DB replaces other sessions' fixtures; back up the triple first and restore it at the end.

## Self-assessment
Step 4 is the one I am least sure about, on one point: whether `measure(scrollRef)` returns window coordinates on the same origin as RNGH's `absoluteY` on Android. Both documents say "relative to the window", and Fabric's `_measure` reports against the root surface, but I could not run it, and a status-bar-sized disagreement would shift both zones by about 24 dp without failing any test. Everything else in the step is composed from reads of reanimated 4.5.1's own source (`useScrollOffset` registers by tag, `scrollTo` is a `dispatchCommand`, `setActive` hops to the UI thread itself) and from RN's Android scroll view, where `scrollEnabled=false` guards touch paths only.

## Self-assessment

Two shapes reach the anchor without a pop count, and I picked the threaded param over the navigation-state read on verifiability, not on correctness — both land on the right route.

The navigation-state read is the smaller diff: three files instead of six, no builder signatures widened, and it takes the anchor's `params.id` off the live stack, so it cannot be stale or dropped. Its price is one string. `useNavigation()` inside the edit screen returns the `(app)` Stack (there is no `_layout.tsx` under `stacked/`), and `getState().routes` carries route **names**, which expo-router derives from the file path relative to the nearest layout — `getRoutesCore.js:522` sets `route` from the context key and `:485` strips the layout prefix, so the anchor is named `stacked/transactions/detail/[id]/index`, `/index` and brackets included, and `useScreens.js:381` passes that verbatim as the screen name. That string is not in the generated `Href` union, not produced by `scripts/generate-typed-routes.js`, and not assertable by any suite in this repo: every test here mocks `expo-router` wholesale, so a unit test would compare my hand-built state against my own assumption. Rename a folder, add a layout under `stacked/`, or let expo-router change index collapsing, and `find` returns `undefined`, the fallback branch runs, and the user lands somewhere plausible. That is `STACKED_EDIT_POP_COUNT`'s failure mode in different clothing, and it is the failure mode the ruling exists to remove — a magic value no gate can fail on.

The param costs four hops that can drop it, and I have not made that cost disappear: `useLocalSearchParams` types `originTxId` as `string | undefined` at both readers, and the pop count is no longer available as the answer when it is missing. The answer is `router.back()`, one screen to the stacked commitment payment. It is wrong against acceptance bullet 3 and right against bullet 5 — inside the mirror, no tab bar, Back from it still lands on the screen it was opened from — and no walk in the app reaches it, because both hrefs on the single entry path (`account_detail.hook.ts:248` → `getCommitmentPaymentRoute` → `commitmentEditRoute`) carry the id after step 5. Only a deep link straight to `/stacked/commitments/<id>/edit` produces a stacked edit without one. What the param buys for that price is that every value it depends on sits under a gate that fails: the two builders' query strings are asserted as literals in two suites, the emit sites are asserted in two hook suites, and the tabbed no-param case is asserted in three places, which turns acceptance bullet 4 from a claim into a test. I checked the one thing that could have killed it before choosing: a query-suffixed template literal is assignable to the generated `Href`, probed at this checkout with both builders' exact return types passed to `router.push`, typecheck clean and the probe removed. The part I am least sure of is the fallback's wrongness rather than its reachability — if a later ticket adds a second entry into the subtree and forgets the third argument, the user gets the payment instead of the transaction, silently. The named guard is the Screens walk plus the fact that the third argument is the only reason the builders take one.

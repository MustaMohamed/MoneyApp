## Untested inputs
- The holder's identity: SQLite sees only "another connection", so the worker stands for both the main connection and another exclusive transaction (steps 4, 5). A single-threaded synchronous bridge cannot hold and wait on one thread.
- Another caller's read on the main connection between BEGIN and the first write: covered by a read inside the task on the same connection, which shares one snapshot, not by two concurrent callers (step 1).
- Main-connection reads queued behind a waiting write: device timing, not asserted (step 1).
- The caller's error field on a lock timeout: the existing store suites assert each field on a repository rejection, and a timeout is an ordinary rejection. Housekeeping staying unmarked after a failure is `__tests__/commitment.store.test.ts:315-330` (steps 2-5).

## Risks
- If better-sqlite3 will not load inside a Jest `worker_threads` Worker, the holder moves to a `node -e` child process on the same file; the cases stay as written.
- Foreign keys turn on for exclusive connections. An exclusive write that succeeded only because they were off now fails on a device database with dangling references. Jest already runs these writes with foreign keys on (`budget.repository.copy_atomic.test.ts:41`, `src/test_helpers/sqlite_fixtures.ts:36`).
- A re-pointed suite whose `BEGIN IMMEDIATE` reaches a recorder instead of the real db still passes but makes its atomicity cases vacuous; the mutation check above catches this.
- A write on the main connection issued from inside an exclusive task would now wait the full bound and then fail. No task does this today; every task passes its own `txn`/`tx`.
- The bound value: the ticket names none. The plan takes Android's framework default, 2500 ms, because the ticket's Danger weighs frozen reads against failed saves.

## Self-assessment
I am least sure about the test harness in step 1. The overlap cases depend on a better-sqlite3 lock holder running in a separate thread while the Jest thread blocks inside SQLite's busy handler. They also depend on a bridge faithful enough to expo-sqlite (timeout 0, foreign keys off, the library's own transaction methods) that the suite fails at the base commit for the lock and for no other reason. If either piece does not hold, the gate the Rules ask for cannot be shown, though the app change in steps 1-5 is still correct. The 2500 ms bound is the plan's own choice and the reviewer can contest it.

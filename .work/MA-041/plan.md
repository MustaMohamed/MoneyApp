# MA-041 — the transaction detail's data slot is keyed by the copy that owns it

base: a79f361bc330d919495ee2ea2eaba913e8958569 · verify: emulator · flags: none · expected diff: ~220 lines

The owner key is per mount, not per route id: the tabbed detail for transaction A can be mounted under a stacked detail for transaction A (`src/app/(app)/(tabs)/transactions/detail/[id]/index.tsx` and `src/app/(app)/stacked/transactions/detail/[id]/index.tsx` re-export the same screen, and the tab stack stays mounted under the `(app)` Stack), so a route-id key would still let one copy's release take the other's data — Acceptance line 7. `useId()` supplies it: the renderer mints it from a module-global counter (`node_modules/react-native/Libraries/Renderer/implementations/ReactFabric-dev.js:6881-6888`), so it is unique per mount and stable across re-renders and re-freezes. Precedent in-tree: `src/components/ui/hero_glow.tsx:13`.

## Steps

### 1. Each copy owns its own load status, reload counter and delete-confirm

- File: `src/modules/transactions/screens/transactions/detail/detail.state.ts`; `src/modules/transactions/screens/transactions/detail/detail.hook.ts` (`useTransactionDetail`)
- Change: the shape becomes `{ entries: Record<string, TxDetailUiEntry> }`, where `TxDetailUiEntry` is today's seven fields (`activeId`, `status`, `revalidating`, `refreshError`, `confirmVisible`, `deleting`, `reloadKey`) unchanged in meaning. Every action takes `owner` as its first argument (`beginLoad(owner, id, preserveData)`, `resolve(owner, id)`, `resolveNotFound(owner, id)`, `failLoad(owner, id, preserveData)`, `setConfirmVisible(owner, v)`, `setDeleting(owner, v)`, `bumpReload(owner)`), writes only that owner's entry, and keeps the existing `activeId === id` guard *inside* the entry so a completion for a route id the same copy has moved off is still dropped. Add `release: (owner: string) => void` deleting one key; `reset()` stays the whole-store reset (`set({ entries: {} })`). Export a frozen `INITIAL_ENTRY` so a missing entry reads as today's initial values with a stable identity. In the hook: `const owner = useId()` at the top, `useTxDetailState(useShallow((s) => s.entries[owner] ?? INITIAL_ENTRY))`, `owner` threaded through every action call and added to the load effect's dependency array, and the unmount cleanup calls `releaseUi(owner)` in place of `resetUi()`. `resetData()` in that same cleanup is untouched here — step 2 owns it, and until then the focus re-claim at `detail.hook.ts:136-140` keeps working unchanged because the data store still has one slot.
- Test: `__tests__/screens/transactions/detail/detail_state.test.ts`, rewritten to drive two literal owners (`'owner-a'`, `'owner-b'`): every existing case moves to `owner-a` and reads `entries['owner-a']`, plus new cases — `beginLoad('owner-b', …)` leaves `owner-a`'s status, `reloadKey` and `confirmVisible` byte-identical; `bumpReload('owner-b')` does not move `owner-a`'s `reloadKey`; `release('owner-b')` leaves `entries['owner-a']` and removes only `owner-b`; `resolve('owner-a', 't1')` after `beginLoad('owner-a', 't2')` is still ignored. Owner strings are literals here — never assert a `useId()` value.

### 2. Each copy owns its own transaction, and refreshes on a write rather than on a lost slot

- File: `src/modules/transactions/screens/transactions/detail/detail.store.ts`; `src/modules/transactions/screens/transactions/detail/detail.hook.ts`
- Change: the shape becomes `{ entries: Record<string, TxDetailEntry> }` with `TxDetailEntry = { txId: string | undefined; tx: Transaction | null; budget: Budget | undefined; loadedAtVersion: number | undefined }`. `setTx(owner, txId, tx, loadedAtVersion, budget?)` replaces that owner's entry and keeps today's budget-preservation invariant scoped to the entry (carry the existing `budget` forward only when the entry's `txId` matches and `tx.budget_id` is unchanged); `setBudget(owner, txId, budgetId, budget)` writes only when that owner's entry still holds `txId` and `tx.budget_id === budgetId`; `clearForId(owner, txId)` sets `{ txId, tx: null, budget: undefined, loadedAtVersion: undefined }` for that owner alone; `release(owner)` deletes one key; `reset()` stays `set({ entries: {} })`. In the hook: read the entry through `useShallow((s) => s.entries[owner] ?? INITIAL_ENTRY)`, compute `preserveData` from that owner's entry, thread `owner` through the four data calls, and release the data entry on unmount. The load effect captures `useTransactionStore.getState().mutationVersion` **before** calling `getById` and passes that value to `setTx` — capturing after the await would stamp a snapshot as fresher than it is, so a write landing mid-read must leave the entry stale. The focus effect at `detail.hook.ts:136-140` replaces the slot re-claim with the staleness gate: bump when this owner's entry is not claimed for `id`, or when it holds a transaction (`tx !== null`) whose `loadedAtVersion` differs from the store's current `mutationVersion`; a mid-flight entry (`tx === null`) never bumps, which is what keeps mount from firing a second `getById`. The comment above the effect changes with it — the store no longer holds one slot.
- Test: `__tests__/screens/transactions/detail/detail_store.test.ts`, rewritten on two literal owners — `setTx` on `owner-b` leaves `owner-a`'s `tx`, `budget` and `loadedAtVersion` untouched; `setBudget` for a transaction the owner has moved off is dropped; `clearForId` clears one owner only; `release('owner-b')` leaves `entries['owner-a']` intact; `setTx` preserves a hydrated budget across a reload of the same transaction and drops it when `budget_id` changes. And `__tests__/screens/transactions/detail/detail_hook.test.ts`: give the `useTransactionStore` mock a mutable `mutationVersion` field (the `dashboard_hook.test.ts:323` pattern — the mock lacks it today, and with both sides `undefined` the gate would pass at base and at head, which `.claude/rules/review.md` § Gates forbids), then replace the `useTransactionDetail focus re-claim` suite (`detail_hook.test.ts:372`) with: focus with nothing written leaves `getById` at one call; focus after `mutationVersion` bumps re-queries and renders the new value; two hooks mounted on different ids each read their own transaction, and unmounting one leaves the other's `state.tx` intact with no further `getById` on its next focus. Two more cases carry the design: **two hooks mounted on the same id** — `renderHook(() => useTransactionDetail(linkedTransaction.id))` twice, unmount the second, the first still has `state.tx` and its next focus leaves `getById` at two calls; this is the only case that separates the owner key from a `txId` key, which would let the second copy's release wipe the first's entry (Acceptance lines 2 and 7, and the same-transaction-twice scenario in the header). And the **delete half of Acceptance line 3**, on that same pair: bump `mutationVersion` with `getById.mockResolvedValue(null)` and refocus the second copy — its `viewState` is `notFound` while the first copy's `state.tx` is unchanged, which fails if `clearForId` writes `entries` wholesale the way it writes the slot today (`detail.store.ts:39`). Two roots do mint distinct owners: the reconciler's `useId` counter is module-global and never reset per root (`node_modules/react-reconciler/cjs/react-reconciler.development.js:6674`, declared at `:17827`). `mockFocusEffect.current` holds only the most recently registered callback (`detail_hook.test.ts:30`), so capture each copy's as it mounts and fire the one the case means. Both copies still resolve through the shared `getById` mock, so use `mockImplementation((id) => …)` as the existing route-change case at `:270` does.

## Risks

- Owner uniqueness rests on `useId()` being counter-derived rather than tree-position-derived; a renderer that hydrates (never, in this app) would mint colliding ids for identically-shaped copies.
- If the hook test's `useTransactionStore` mock is left without a mutable `mutationVersion`, the staleness gate passes at base and at head and asserts nothing.
- `freezeOnBlur: true` on both Stacks (`src/app/(app)/_layout.tsx:26`, `(tabs)/transactions/_layout.tsx`) means a blurred copy does not re-render; releasing an entry anywhere but unmount would blank the copy that owns it on unfreeze.
- An entry leaks for the life of the process if a copy is torn down without its cleanup running; bounded by the number of details ever mounted, and `reset()` still clears everything.

## Self-assessment

The predicate in the step 2 focus gate is the part I am least sure about, because it has to serve three entry states with one expression: mid-flight (`tx === null`, `loadedAtVersion === undefined`) must not bump or every mount fires a second `getById` and the existing one-call assertion breaks; loaded-and-current must not bump, which is Acceptance line 2; loaded-and-stale must bump, which is line 3. The fourth state — `notFound` and `firstLoadError`, both `tx === null` after the load settled — falls out as "never re-queries on focus", which matches today's behaviour (`clearForId` leaves `txId === id`, so today's gate does not fire either) but is arguably wrong on its own terms, and the retry button is the only way out of it. I kept today's behaviour rather than widen the ticket.

# MA-081 — Reorder data path: renumber active accounts in one transaction, the store action
base: 76f62828fd4d8633f32e33b0488ebfe57dd04157 · verify: none · flags: none · expected diff: ~65 lines

Four files outside tests, three steps. One new suite carries every repository case because its transaction mock must be real BEGIN/COMMIT/ROLLBACK; the three existing repository suites keep their pass-through mock and stay untouched.

## Steps
### 1. One guarded statement writes one active row's position and nothing else
- File: `src/modules/accounts/database/accounts.ts` (after `setAccountUnarchived`, `:167-184`)
- Change: `export async function setAccountSortOrder(db: SQLiteDatabase, id: string, sortOrder: number): Promise<number>` runs `UPDATE accounts SET sort_order = ? WHERE id = ? AND is_archived = 0 AND is_deleted = 0` and returns `result.changes`, the shape of `setAccountBalance` (`:186-199`). No `updated_at` parameter and no `updated_at` in the SET list; a one-line comment states that a position change is not an edit of the row. No transaction here: the caller owns it.
- Test: `first` · `__tests__/account.repository.reorder.test.ts`, harness copied from `__tests__/account.repository.delete.test.ts:170-184` (real `BEGIN`/`COMMIT`/`ROLLBACK` over better-sqlite3) with a `seed()` in the shape of `account.repository.unarchive.test.ts:63-70`: active `a` at 0, `b` at 0 with a later `created_at`, `c` at 3, `e` at 7; archived `x` at 1; deleted `d` at 2 (`is_archived = 1, is_deleted = 1`). Cases on the query: resolves `1` on an active row and the row differs from before in `sort_order` only, `updated_at` included; resolves `0` on `x`, on `d` and on `missing`, and their rows equal their pre-call values.

### 2. The repository refuses a bad order before the transaction and renumbers 0..n-1 inside it
- File: `src/modules/accounts/repositories/account.errors.ts`; `src/modules/accounts/repositories/account.repository.ts` (`IAccountRepository` `:47-59`, `AccountRepository`); `__tests__/account.store.test.ts:51-65` (`makeRepo` gains `reorder: jest.fn().mockResolvedValue(undefined)` in this step: its literal is typed `IAccountRepository` and `tsconfig.json` includes `**/*.ts`, so the interface change fails `typecheck` until the fixture has it)
- Change: add `export class AccountReorderInvalidError extends Error` (`name = 'AccountReorderInvalidError'`, message `'The order must name every active account exactly once'`), one class for every refusal because the caller has one response to all of them. Add `reorder(orderedIds: string[]): Promise<void>` to the interface and the class, after `unarchive`. Body: `const active = await getAccounts(db)`; throw `AccountReorderInvalidError` when `orderedIds.length !== active.length`, when `new Set(orderedIds).size !== orderedIds.length`, or when any id is not in `active`; that one read covers omitted, duplicated, archived, deleted and unknown ids. Return without a write when `orderedIds` equals `active.map((a) => a.id)` element for element; the read order is the current order, so gaps stay until an order actually changes. Otherwise `db.withTransactionAsync` over `for (const [index, id] of orderedIds.entries())`, calling `setAccountSortOrder(db, id, index)` and throwing `AccountReorderInvalidError` on a count other than `1`, which rolls the loop back if a row left the active set between the read and the write. Import the new query and error; `src/repositories/account.repository.ts` re-exports the type and needs no edit.
- Test: `first` · `__tests__/account.repository.reorder.test.ts`, same seed; its `beforeEach` adds `sqlite.withTransactionAsync.mockClear()` after `seed()`, because that mock is the module-level `jest.fn()` from `jest.setup.js:28`, its `mock.calls` last the whole suite (`jest.config.js` sets no `clearMocks`, and `jest.restoreAllMocks()` only restores spies), so the `not.toHaveBeenCalled()` assertions below go red once the success case has run; `mockClear` keeps the `BEGIN`/`COMMIT`/`ROLLBACK` implementation from `beforeAll`. `reorder(['e','c','b','a'])` stores 0,1,2,3 in that order, `getAll()` returns it and `getByIdsIncludingArchived(['a','b','c','e'])` returns `e,c,b,a` (the lookup reader at `accounts.ts:40`, the third `ORDER BY sort_order`); a second `new AccountRepository().getAll()` reads the same order (the relaunch case, same database). `reorder(['a','b','c','e'])` with the seeded gaps and the `a`/`b` duplicate: writes nothing, `sqlite.withTransactionAsync` not called, positions still 0,0,3,7. `reorder(['b','a','c','e'])` collapses them to 0..3. Every non-`sort_order` column of every row, `updated_at` included, equals its pre-call value after a successful reorder; `x` keeps 1 and `d` keeps 2. `it.each` over `['a','b','c']` (omits), `['a','a','c','e']` (duplicate), `['a','b','c','x']` (archived), `['a','b','c','d']` (deleted), `['a','b','c','nope']` (unknown), `[]`: rejects with `AccountReorderInvalidError`, `withTransactionAsync` not called, every position unchanged. Atomicity: `const real = accountsDb.setAccountSortOrder;` bound before `jest.spyOn(accountsDb, 'setAccountSortOrder').mockImplementationOnce(real).mockRejectedValueOnce(new Error('sort write failed'))` (the spy replaces the export, so `real` read after it is the spy) so the first row is written inside the transaction and the second call throws; `reorder(['e','c','b','a'])` rejects with that error and every position, `e`'s included, reads its seeded value. This case fails under the pass-through mock at `src/test_helpers/sqlite.ts:36` and passes only through the harness's `ROLLBACK`.

### 3. The store exposes `reorderAccounts`, reloading after success and after failure
- File: `src/modules/accounts/store/account.store.ts` (`AccountStore` `:31-43`, the actions object `:143-167`); `makeRepo` already carries `reorder` from step 2
- Change: `reorderAccounts: (orderedIds: string[]) => Promise<void>`. It calls `repo.reorder(orderedIds)`; on rejection it logs under the `[accountStore] reorderAccounts failed:` tag, runs `get().loadAccounts().catch(() => undefined)` so the list re-reads the saved order (a refusal means the list the screen ordered from was stale), then rethrows the write error; on success it reloads the same way. `writeThenReload` (`:53-65`) keeps its no-reload-on-failure contract; the sibling tests at `account.store.test.ts:629,687,757` assert it, so this action gets its own body or a variant flag, never a change to the shared path. No optimistic publish: `accounts` changes only through `loadAccounts`, as for every other action.
- Test: `first` · `__tests__/account.store.test.ts`, a `describe('accountStore.reorderAccounts')` after `unarchiveAccount`: delegates to `repo.reorder` with the ids and publishes the list `getAll` returns on the reload; rejects with the repository error, and by then `getAll` has run twice (load, failure reload) and `accounts` equals what the second read returned; resolves when the write lands and only the reload fails, `loadError` true; a failed write whose reload also fails rejects with the write error, not the reload error, `loadError` true.

## Risks
- The no-op rule reads "current order" as the id sequence `getAccounts` returns, so a same-order call leaves existing gaps in place; if the reviewer reads Acceptance as "the first reorder call renumbers", step 2's no-op branch also compares each row's `sort_order` to its index and writes when any differs.
- `jest.spyOn(accountsDb, 'setAccountSortOrder')` intercepts the repository's call only while the repository imports it by name from `'../database/accounts'` (Babel's CJS interop reads the property at call time); the delete suite's spy on `clearCommitmentAccount` rests on the same fact. A local alias breaks the atomicity test, not the code.
- MA-082 may need the list to hold the dropped order during the reload round trip; under this plan that is screen state, and moving it into the store is an amendment to step 3, not a silent addition.
- `AccountReorderInvalidError` is one class; if MA-082's copy wants to tell "list changed under you" from "bad input", a second read of the strays would be needed. Nothing in #529 or #530's Acceptance asks for that.

## Self-assessment
Step 3 is the one I am least sure of. Acceptance reads "on failure the store's list reads in the saved order", and Context says that failure-path reload is the new action's own; both are satisfied by a reload after the rejection, but the sentence would also fit a store that publishes the dropped order first and restores on failure. I chose the reload-only shape because every sibling action changes `accounts` through `loadAccounts` alone, because the refusal path is exactly the case where the store's list was stale and a reload is what fixes it, and because the interim order during the drop belongs to the gesture the screen ticket owns. If the reviewer wants the optimistic publish here, the store step gains one `set({ accounts })` from the store's own rows before the write and one test asserting the order mid-flight through a deferred `repo.reorder`.

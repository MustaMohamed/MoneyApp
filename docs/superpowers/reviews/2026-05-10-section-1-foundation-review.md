## Blockers (must fix before merge)

### B1 — `tsconfig.json` missing newline at end of file

The diff shows `\ No newline at end of file` on the last line of `tsconfig.json`. This is not cosmetic. Prettier's `endOfLine` and `insertFinalNewline` expectations are enforced by the `format:check` script. More critically, some tsc invocations on Windows CI nodes can choke on a JSON file without a trailing newline, and the husky pre-commit hook runs `prettier --check`. If this slips into main and a team member's local Prettier rewrites it, the resulting diff is misleading noise in an unrelated PR.

Fix: add a trailing newline to `/home/user/MoneyApp/tsconfig.json` (one character change, no content change).

## Important (should fix before merge or before §2 starts)

### I1 — `focus:border-gold-500` dropped from `Input` without documentation

The spec (§1.5, `input.tsx` code block) explicitly specifies `'focus:border-gold-500'` as the third class in the `cn()` call. The plan's Task 10 code block silently dropped it. The implementation follows the plan (no `focus:` class present). Neither the plan revision nor the implementation commit message documents this as a deliberate removal or a known NativeWind limitation.

This matters for §2: Onboarding forms use `Input`, and the gold focus ring is part of Marcus's locked Cairo Nights brand contract for input interaction. If `focus:` pseudo-classes are unsupported by NativeWind v5 preview.3 + react-native-css 3.0.7 in this Expo Go context, that needs to be an explicit recorded decision — not a silent omission.

Required action: one of the following.
1. Confirm that `focus:` variant is not supported in the NativeWind v5 / react-native-css 3.x transform pipeline in Expo Go, add a one-line comment to `input.tsx` documenting this, and file an open question in the §2 spec for how focus state will be communicated visually (e.g., via `onFocus`/`onBlur` state + conditional className prop from the consumer).
2. Or restore `'focus:border-gold-500'` if it does work.

Either outcome is acceptable. The silence is not.

### I2 — `Button` ref attaches to inner `Pressable`, not outer `LinearGradient` wrapper (primary variant)

When `variant === 'primary'`, the component tree is `LinearGradient > Pressable`. The `ref` is forwarded to `Pressable`. A caller who does `const btnRef = useRef(); <Button ref={btnRef} />` and then calls `btnRef.current.measure()` will get the Pressable's dimensions — which are identical to LinearGradient's because Pressable fills it — but a caller who uses the ref for layout measurement relative to the screen (e.g., `measureInWindow`) will get coordinates of the Pressable, which is correct. However, any future use of the ref for animation targets (Reanimated's `animatedRef`, used in §5 Dashboard hero CTA) needs the outermost view, which is LinearGradient here. The current forwarding is correct for `accessibilityFocus` and `onPress` programmatic triggering, but will silently give wrong results for `measureInWindow` on the gradient wrapper.

This is a forward-looking risk for §5, not a bug today. Required action: add a code comment on the `forwardRef` call noting that `ref` targets the inner `Pressable` (not `LinearGradient`), and that callers needing the gradient container's layout must use a wrapper `View` with their own ref. This documents the contract so §5's developer does not get silently burned.

## Nits (optional, no merge gate)

### N1 — Version drift: `tailwindcss ^4.3.0` in `package.json` vs `^4.1.11` in spec version matrix

The spec version matrix lists `tailwindcss ^4.1.11` (the minimum required by nativewind's peer dep) but `package.json` records `^4.3.0` and the lock resolves to `4.3.0`. This is within semver range (`^4.1.11` allows up to `<5.0.0`) and nativewind's peer constraint explicitly states `>4.1.11`, so `4.3.0` is valid. However, the spec's version matrix should be updated to reflect what was actually installed, or annotated to say "minimum version; actual installed version may be higher." Currently a reader of the spec would expect `^4.1.11` and find `^4.3.0` in the repo — minor confusion.

### N2 — `nativewind-env.d.ts` added to `tsconfig.json` includes without plan coverage

The file was auto-generated by `react-native-css` and is referenced correctly in `tsconfig.json`. Good catch by dev. But the plan's Task 2, Step 3 does not mention adding it to `include`. The next developer reading the plan to understand the build setup will find an unexplained include. Add a comment to the plan (or note in §2's prerequisites section) that `nativewind-env.d.ts` is generated by `react-native-css` on first Metro run and should be committed as generated infrastructure.

### N3 — `Button.label` is `string`, not `ReactNode`

`label: string` is correct for the current use cases and matches the spec. However, §2 Onboarding will almost certainly need a `Button` with an icon alongside the label (e.g., "Continue →" with a chevron icon). Locking to `string` now means a breaking interface change when that need arises — either rename the prop to `labelText` or widen to `ReactNode | string`. Not a blocker for §1, but flag this when writing the §2 spec so Marcus can lock the interface before §2 dev starts.

### N4 — `screens/dev/primitives/index.tsx` uses `useState`/`useSharedValue` guard from CLAUDE.md incorrectly applied

The CLAUDE.md anatomy rule says `index.tsx` (UI) — "no useState/useSharedValue." The dev preview screen has none of these, so it is compliant. But it does inline `if (!__DEV__) return null` inside the default export function body. This is a guard expression, not state. No issue. Noting it explicitly in case a future reviewer flags it: this is fine.

### N5 — `tailwind.config.js` content glob missing `utils/**/*.{ts,tsx}`

The content array scans `app/`, `screens/`, and `components/` for class names to include in the purged build. The `utils/` directory contains `cn.ts` (no Tailwind classes) but future utilities may compose Tailwind strings directly. More importantly, `screens/dev/primitives/index.tsx` uses `ScrollView className="flex-1 bg-bg p-4"` — this is covered by the `screens/` glob. However, `constants/` is also not in the content array. Currently `theme_tokens.ts` contains only hex strings (not class names), so no purge issue exists today. This will become a real bug if a developer ever constructs a Tailwind class string in `constants/` or `utils/` and wonders why it is purged in production. Not a §1 risk; flag for §3 when reviewing the plan.

## Praise

**Palette architecture is exactly right.** `constants/theme_tokens.ts` as the sole source of truth with `tailwind.config.js` importing from it (no hex literals) — and the lint rule enforcing it — is the correct pattern. The single-source principle will pay compounding dividends across §2-9.

**`tsx/cjs` loader decision was correct.** Node v22 + TypeScript imports is a real problem; registering `tsx/cjs` at the top of `tailwind.config.js` is the minimal, build-time-only solution with zero runtime footprint. Documenting it with a comment explaining why is exactly right.

**`tsconfig.json` deviation (#1 in known deviations) is correct.** Adding `"jest"` alongside `"nativewind/types"` is the right fix. TypeScript auto-includes `@types/*` only when no explicit `types` array is present. The alternative — removing the explicit `types` array entirely — would lose the NativeWind `className` typing on RN components, which would silently break on the next `tsc` run.

**Test file extension deviation (#2) is correct.** `.test.tsx` for files containing JSX render calls is standard and matches the existing project pattern. Using `.test.ts` for JSX would cause a Babel transform error.

**Button test rewrite (#3) is correct.** `UNSAFE_getByType(Pressable)` does not work at the RNTL host layer. The dev's approach — `UNSAFE_getAllByType(View)` then filtering by `accessibilityRole === 'button'` — is the right implementation-aware workaround given the mock. `fireEvent.press()` over `getByRole('button').props.onPress()` is strictly better (it follows the RNTL event propagation chain, catches `onPressIn`/`onPressOut` side effects, and does not require the internal prop to be exactly `onPress`).

**`hasError = false` default in `Input` (implicit deviation from spec's no-default version) is correct.** Defaulting to `false` prevents a downstream `undefined` value from propagating through the ternary, which would have resolved to `'border-border'` anyway — but TypeScript strict mode could complain about the prop type if a consumer does `hasError={someNullableBoolean}`. The plan's version with the explicit default is the better API.

**`GoldTokens` import in `button.tsx` for `LinearGradient` colors is correct.** The spec note (§1.5) called for this exact pattern to keep the component token-honest even though the lint rule does not cover JSX props. The comment confirming the hex values is appropriate.

**44px `hitSlop` on `Pressable` is correct.** This is a non-negotiable Apple HIG / WCAG 2.1 requirement (minimum 44x44pt touch target). Baking it into the primitive means no downstream component can accidentally ship a sub-44pt target when using the `Pressable` primitive.

**908 tests across 107 suites with all coverage thresholds met is a strong baseline.** The new §1 tests are well-targeted: they test the contract (className strings, prop forwarding, error states) rather than NativeWind's runtime behavior, which would be untestable in Jest. The test strategy note in the plan is accurate and the implementation follows it correctly.

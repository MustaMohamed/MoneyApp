# MA-004 — Onboarding shell: four fixed tracks and an honest busy CTA

## Summary

Give all four onboarding routes one shared chrome — header, progress rail, content viewport, and a footer whose status track and CTA never move — and make a busy button say what it is actually doing.

## Details

Today the four onboarding routes each assemble their own chrome, share a row of progress dots, and put their CTA in a bar that differs between screens. The approved design freezes one shell for all four: a fixed-height header, a fixed-height progress rail, a flexible scrolling content viewport, and a footer built from a permanently mounted status track above the primary action. Exact heights and behaviour are in `spec.md` § *Product & UX — Shell*; the reference frames are mockup A1, A2 and A3.

**The status track is the load-bearing part.** It is always mounted and never empty. When nothing is wrong it carries the one footnote that screen genuinely wants — a different line per screen, listed in the spec — and when a step fails, the error replaces that footnote **in the identical box**. The footer does not grow, the button does not move, and retry is the primary action itself, so a second button never appears. It is announced as a live region so a screen reader hears a failure without focus jumping. It is plain text, not a bordered alert component: an alert brings its own padding and would make the footer taller in exactly the state the track exists to keep still.

**The status track is delivered here and fed by later tasks.** Nothing in this task produces a real failure message — the four routes still hold their current bodies and their current save paths. This task proves the track can hold and swap a message; MA-005, MA-008, MA-009, MA-010, MA-011 and MA-012 are the tasks that put real failures into it. Force a message through it in the emulator run rather than waiting for a real one.

**The progress rail** shows four segments and a label reading which step of four this is plus that step's name. Advancing changes a segment's colour, never its width. The segments themselves are hidden from assistive technology; the label carries the meaning.

**The welcome route's header is a variant, not a different header.** It swaps the back affordance for the app mark and wordmark plus a small right-aligned setup label, at the same track height as every other route. It consumes the in-app mark delivered by MA-003.

**This task changes no navigation.** Which route the user lands on, when the step is persisted, and whether a swipe-back can desynchronise it are MA-005's, deliberately kept out of this diff so that a chrome review is a chrome review. Walking the flow here should reach the dashboard exactly as it does today, by exactly the route it does today.

### A busy button must stop lying

Every primary action in the app currently reads "Loading..." while it works, because the shared button hardcodes that string. The design needs "Saving…" on the account form and "Opening…" on the finish button. One optional label, supplied by the caller, fixes it everywhere; callers that supply nothing keep exactly today's behaviour.

The same change adds the spinner the design shows on a busy button. The shared button accepts a loading flag today and does nothing with it beyond swapping the label — the flag never reaches the underlying primitive, which has no such concept.

**Understand the blast radius before planning this.** Roughly a dozen call sites across the app pass that loading flag today — confirmation dialogs and sheets, the commitment form, the pay sheet, the transaction form, the category sheet, account detail, adjust-balance, balance-review, the startup error screen. **Every one of them gains a spinner in this task**, and none of them is an onboarding screen. That is why this task runs on the emulator rather than resting on a unit test, and why its device QA at gate 3 has to leave onboarding and press a saving button somewhere else in the app.

**The gold gradient on the primary button stays.** The mockup draws a flat accent fill; the shipped wrapper paints a two-stop gold gradient underneath. Keeping the wrapper is a recorded, deliberate deviation — flattening it would re-skin every CTA in the app, which `scope.md` excludes. See `spec.md` § *Known design/codebase disagreements*, item 1. Do not "fix" it here.

**All four routes adopt the shell in this task, with their current content unchanged.** They will look transitional — new chrome, old bodies — and that is fine; each body is rebuilt in its own task. Merging this alone leaves a working app. The progress-dots component the four routes share today has no other consumer and goes with them.

**Done when:** all four onboarding routes render the same four tracks at the same offsets; the status track holds its per-screen footnote and swaps to a forced error message without the button moving a pixel; a test asserts the shell's track heights against the named geometry values from MA-001; a busy button renders a spinner and a caller-supplied label, and a test covers both the supplied and the omitted case; a busy button **outside onboarding** has been watched on the emulator with its new spinner; and walking the whole flow reaches the dashboard exactly as it does today.

## Plan

### Summary

- Add one geometry token (`Size.progressRail`) and the shell's copy to `strings.ts`. Everything else the shell measures itself against already exists: `Size.headerHeight`, `Size.statusTrack`, `Size.ctaHeight` (`src/constants/theme.ts:136-209`).
- Split the busy-button decision out of `src/components/ui/button.tsx` into a pure `button.content.ts` (label ↔ `loadingLabel` ↔ `Strings.loading`, spinner on/off, spinner colour per variant) so both Done-when cases are provable in a logic-only `.ts` test, then wire `Spinner` and the new `loadingLabel?: string` prop into the wrapper. - Build `OnboardingShell` under `src/modules/onboarding/components/onboarding_shell/`, with the checkable parts (track heights, progress-rail model, status-track text + live-region mapping) in a pure `onboarding_shell.geometry.ts` sibling — the same shape MA-002 shipped as `display_headline.geometry.ts` and MA-003 as `logo_mark.a11y.ts`.

- No new dependency, no native change, no migration, no navigation change. No critical trigger fires — see § *Critical triggers* at the end.

### Decisions, and the evidence for each

Everything here was read in the tree or in the packaged `heroui-native@1.0.8` source. `node_modules/` is absent from this checkout, so HeroUI facts were verified against the published tarball (`registry.npmjs.org/heroui-native/-/heroui-native-1.0.8.tgz`, `package/src/...`), which is the same code `package.json:49` resolves.

|---|---|---|
| 1 | **HeroUI `Button` has no `isLoading` and never will here — the spinner is a child.** `package/src/components/button/button.types.ts:41-66` has no loading prop; the library's own recipe (`button.md`, § *Loading State with Spinner*) is `<Button>{isDownloading ? <Spinner color={…}/> : 'Download now'}</Button>`. | 9 | **The shell does not own a `ScrollView`.** `more_accounts/index.tsx:55` renders a `FlashList`; wrapping the shell's viewport in `ScreenScroll` would nest a virtualised list in a scroll view. | 12 | **N3's footnote follows `spec.md`, not the A2 frame.** Spec § *Shell*: `One account is enough to start.

# MA-008 — Onboarding adopts the shared account form

## Summary

Delete onboarding's copy of the account form, host the shared one instead, and fix the two onboarding-side defects that only stop being duplicated once there is one form.

## Details

This is the second half of the de-duplication MA-007 began, and it is the one that touches the live first-run path. When it merges, the second onboarding step should look and behave as it does today — same fields, same order, same copy — but rendered by the Accounts module's form, with onboarding keeping only what is genuinely its own: the starting currency, its own copy, the back behaviour, the step it persists after a save, and where it goes next.

**Everything onboarding duplicated goes in this task**: its copy of the form body, its copy of the submission mapping, its own twelve-colour list, and its hand-rolled swatch row. The swatch row is replaced by the colour sheet MA-006 built — onboarding picks that up as a side effect of adopting the shared form, and it is the first visible change on this screen.

**The starting currency is onboarding's, not the form's.** The form takes a starting currency from its host; onboarding passes the base currency the user chose on the first step. Settings passes its own default. Neither knows about the other.

### Two live defects fixed here

- **The "adding another account" flag is a string tested for truthiness.** An explicit `false` therefore takes the add-more branch, and the stack's own parameter type claims the value is a boolean when it is not. It must be compared exactly, and the type must stop lying. MA-011 depends on this working — its whole add-another round trip runs through this flag.
- **The screen reloads the account list on mount** even though startup already loaded it and saving publishes its own refresh. The load goes.

### The post-save checkpoint

This is behaviour the mockup draws and no task owned. Frame A3's caption states it and C4/C6 are where a user meets it: **when the account insert succeeds but the step write fails, the retry repeats only the step write and never re-inserts the account.**

The failure the user sees is about the step, not the data. Their account is on disk. Tapping the primary action again must not produce a second account — and it must not be prevented from retrying either, because the step really does need writing. The error renders in the shell's status track, which MA-004 delivered; the form reports its failure and the host renders it.

This is the interaction between the guarded save path from MA-007 and the persist-before-navigate ordering from MA-005, and it is the single most valuable thing to force on the emulator in this task: make the step write fail with an account already inserted, tap retry, and count the rows.

**Behaviour that must be preserved exactly:** duplicate names still rejected case-insensitively after trimming; current balance still equals opening balance; credit-only values still absent rather than zero on non-credit accounts; and a successful save still advances to the more-accounts step, persisting before it navigates and replacing rather than pushing, per MA-005.

**Done when:** both entry points render from the same form, and the duplicated form body, submission mapping and colour list exist in exactly zero places; the add-more flag is compared exactly, its declared type matches what is actually passed, and a test covers the explicit-`false` case that is broken today; no onboarding route loads the account list itself; a forced step-write failure after a successful insert leaves exactly one account row, shows the error in the status track, and retries into the next step without inserting again; and creating an account from onboarding and from Settings on the emulator both produce a correct row, checked against the database.

## Plan

### Summary

- **Onboarding's N2 becomes a host, nothing more.** `add_account.hook.ts` drops its own RHF/Zod setup, its own `ACCOUNT_COLORS`, and its own `parseFloat` submission mapping, and calls `useAccountForm` with three things onboarding actually owns: the base currency, `Strings.n2SaveError`, and an `onSaved` that writes the step and replaces the route. `index.tsx` drops ~280 lines of duplicated field markup and renders `<AccountForm form={form} ownerId="onboarding/add_account" />` inside the shell it already has.
- **One re-entry guard and one busy flag on the save path — the form's.** `runOnboardingTransition` is *not* nested inside `onSaved`; the tail is written inline from `resolveOnboardingStep` + `ONBOARDING_STEP_HREF`, and it throws rather than swallowing, so `useAccountForm`'s `inserted` latch and `failSave` are what implement the post-save checkpoint. The transition state survives on this screen for `onBack` only, and the two are interlocked explicitly in both directions.
- **`useAccountForm.submit` must skip re-validation once `inserted` is latched** — **D9, added at plan review.** Without it the post-save checkpoint is unreachable on a real store: `addAccount` awaits its own `loadAccounts()` (`account.store.ts:85`), the memoised schema rebuilds from an `accounts` array that now contains the row just written (`use_account_form.hook.ts:50-51`), and the retry tap fails `errNameDuplicate` inside `handleSubmit` before `onValid` ever runs. This is a change to `use_account_form.hook.ts`, which the rest of this plan treats as untouched.
- **`isAddingMore` is compared with `=== 'true'`**, once, at the top of the hook, and `OnboardingStackParams` stops declaring it a boolean.
- **All three onboarding `loadAccounts()` call sites go** — N2, N3 and N4 — because `spec.md:502` names exactly those three and the Done-when is the plural one.
- **`CurrencySelector` gains the accessible name** onboarding is otherwise about to lose (flagged for this task at MA-007 step 5, `MA-007.md:108`).
- **Tests:** `__tests__/screens/onboarding_add_account.hook.test.ts` is rewritten to **seventeen** cases against the new hook shape, including the explicit-`false` case that is broken today (both on save and on back), the retry-writes-only-the-step case, both halves of the interlock, both directions of the status-track precedence, and the back-inside-validation race. `__tests__/account_form.hook.test.ts` gains one case for D9. Four other suites are cited rather than duplicated.
- **Emulator:** four scoped scenarios, one of which forces `setStep` to reject exactly once with an account already inserted and counts rows in SQLite.

**D2 — one status track, two writers, stated precedence. *Corrected at plan review.*** `OnboardingShell` takes a single `statusMessage` (`onboarding_shell/index.tsx:19`). After D1 the save path writes `useAccountFormState.errorMessage` and the back path writes `useAddAccountTransitionState.statusMessage`. The hook merges them as:

```ts
statusMessage: transitionStatusMessage || formErrorMessage
```

Transition wins because it is the later event in the only sequence where both are set: a failed save leaves `errorMessage` set, and if the user then taps back and *that* fails, the message the user needs is the one about the chevron. The reverse precedence would pin the stale save error.

**The original argument for why nothing can go stale was wrong, and the fix is mandatory.** It said "`begin()` clears `statusMessage` on every accepted back attempt and `beginSave()` clears `errorMessage` on every accepted save attempt, so neither channel can hold a message from an attempt two operations ago." Each of those clears only *its own* channel — `beginSave` (`account_form.state.ts:47`) sets `{ saving: true, errorMessage: undefined }` and never touches the transition store; `begin` (`onboarding_transition.state.ts:44`) sets `{ busy: true, statusMessage: '' }` and never touches the form store. With a fixed precedence the higher-precedence channel therefore pins: **back fails → user taps Save → save fails → the track still reads `onboardingBackSaveError`**, naming a chevron the user did not touch.

`ready.hook.ts` already hit this and solved it — `handleComplete` calls `useReadyTransitionState.getState().reset()` at the start of every completion attempt, with a comment (`ready.hook.ts:57-61`) saying exactly this. Mirror it: `handleSave` clears the transition channel before it submits (code in step 2.3). The early return on `busy` above it guarantees `reset()` cannot clobber a live back transition. Consequence to accept deliberately: a save that fails *validation* now also clears a standing back error, where today it would leave it up. That is the right way round — the user's latest intent is "save".

Pinned by tests 15 **and 16** (both directions; 16 fails without the `reset()`).

**D3 — the interlock, in both directions, because there are still two guards on this screen.**

- `onBack` returns early when `useAccountFormState.getState().saving` is true. This also makes `spec.md:81` ("Back disabled during the write") true for the first time, and it restores exactly the coverage today's single shared `busy` gave.
- `handleSave` returns early when `useAddAccountTransitionState.getState().busy` is true, **before** calling `submit()`, so nothing is validated and no state moves. Silent, matching `spec.md:492` ("CTA re-entry is ignored while an operation is active") and matching today's behaviour, where `begin()` returns `null` with no message.

Residual, **corrected at plan review**: both checks read a flag that is set *inside* an async callback, so there is a window after a Save tap — the whole of Zod validation — where `saving` is not yet set. The original claim that this window "is identical to `main`'s, so this is not a regression" is **false**. On `main` there is one shared gate and it sits *after* validation (`add_account.hook.ts:75`, inside `onSubmit`): if a Back lands during a Save's validation, Back's `begin()` wins and the Save's own `begin()` then returns `null`, so **`main` inserts nothing**. Under D1/D3 the two guards are separate and `handleSave`'s check runs *before* `submit()`, so the same interleaving inserts a row, writes N3 and fires a second `replace` while the back transition is navigating to welcome. That is a new race, and it is exactly what the dropped `isCurrent()` used to catch. It is closed in D4.

**D4 — what replaces `isCurrent()` on the save path. *Corrected at plan review.*** The only producer of a competing session on this screen is `onBack`; nothing else calls `begin()` on `useAddAccountTransitionState` (grep confirmed: `add_account.hook.ts` is the file's sole consumer, and `add_account.state.ts` creates a per-screen instance, `onboarding_transition.state.ts:34`). **D9 — the post-save checkpoint does not work without a change to `useAccountForm`. *Added at plan review; this is the task's central Done-when clause.***

`submit` is `form.handleSubmit(onValid)` (`use_account_form.hook.ts:80`), so **every** tap re-validates before `onValid` runs. Trace the retry on a real store:

1. Tap 1 validates against a schema built from `accounts = []`, passes, `beginSave()`, `addAccount(...)`.
2. `addAccount` awaits its own `loadAccounts()` (`account.store.ts:82-91`) → the store publishes a new `accounts` array **containing the row just written**.
3. `markInserted()`, then `onSaved()` rejects on the step write → `failSave(n2SaveError)`. So far so good.
4. That publication re-renders the hook: `accounts` is a new reference → `useMemo` rebuilds the schema (`use_account_form.hook.ts:50-51`) → `useZodForm`'s `useEffect` writes it to `schemaRef.current` (`use_zod_form.hook.ts:14-17`), and the resolver reads that ref at validation time.
5. Tap 2 validates against the new schema. `createAddAccountSchema`'s `superRefine` (`add_account.schema.ts:26-29`) compares the draft name case-insensitively after trimming against every loaded account — **including the one this very form just created**. Validation fails with `errNameDuplicate`, `onValid` never runs, no step is written, and the status track keeps the stale `n2SaveError` with `This name is already used` under the name field.

So the retry is impossible except by renaming the account. The `inserted` latch is fine and survives; nothing ever reaches it. The hook's own JSDoc (`use_account_form.hook.ts:27-34`) already promises "the next `submit()` re-runs only this callback" — this makes the code deliver what it documents, so it is this task's, not a new scope.

**The change**, in `use_account_form.hook.ts`:

```ts
const handleSubmit = form.handleSubmit(onValid);

const submit = async () => {
  // Post-save checkpoint (MA-008). Once the row is on disk the draft has
  // already passed validation once, and the schema has since been rebuilt
  // from an accounts array that CONTAINS that row — re-validating fails

  // retry can never reach onSaved. Re-enter the guarded tail directly;
  // onValid's `inserted` check is what keeps addAccount from running twice.
  if (useAccountFormState.getState().inserted) return onValid(form.getValues());

return { form, submit, state: { saving, errorMessage } };
```

#### Claims checked that turned out false, with the correction

**1. The post-save checkpoint cannot work as planned — the retry is eaten by validation, not by the latch. (`use_account_form.hook.ts:80`, `:50-51`; `account.store.ts:82-91`; `add_account.schema.ts:26-29`; `use_zod_form.hook.ts:14-17`)**

The plan asserts the `inserted` latch is what implements the checkpoint and that `use_account_form.hook.ts` needs no change. The latch is fine; nothing reaches it. `submit` is `form.handleSubmit(onValid)`, so tap 2 re-validates first, and by then `addAccount` has awaited its own `loadAccounts()`, the store has republished `accounts` **including the row just written**, the memoised schema has rebuilt, and `useZodForm`'s `schemaRef` has been updated. `superRefine`'s duplicate-name check then rejects the draft against the account this very form created. Result on device: `This name is already used` under the name field, a stale `n2SaveError` in the status track, no step write, no navigation — the retry is only escapable by renaming the account.

The task's Done-when clause "retries into the next step without inserting again" is therefore unproduceable by the plan as written. Added as **D9**, with the exact bypass, the Settings blast-radius argument, and the required test.

**2. #### Defects

**D-1 — `use_account_form.hook.ts:87`: the D9 bypass fires after a *successful* save, not only after a failed one, and re-runs the host's `onSaved`. On Settings that pops two screens.**

The plan and the plan review both justify the blast radius with "`inserted` is only ever true there after a save that already succeeded **and unmounted the screen**" (Plan D9, R8).

# MA-008 — Onboarding adopts the shared account form

## Summary

Delete onboarding's copy of the account form, host the shared one instead, and fix the two onboarding-side defects that only stop being duplicated once there is one form.

## Details

This is the second half of the de-duplication MA-007 began, and it is the one that touches the live first-run path. When it merges, the second onboarding step should look and behave as it does today — same fields, same order, same copy — but rendered by the Accounts module's form, with onboarding keeping only what is genuinely its own: the starting currency, its own copy, the back behaviour, the step it persists after a save, and where it goes next.

**Everything onboarding duplicated goes in this task**: its copy of the form body, its copy of the submission mapping, its own twelve-colour list, and its hand-rolled swatch row. The swatch row is replaced by the colour sheet MA-006 built — onboarding picks that up as a side effect of adopting the shared form, and it is the first visible change on this screen.

**The starting currency is onboarding's, not the form's.** The form takes a starting currency from its host; onboarding passes the base currency the user chose on the first step. Settings passes its own default. Neither knows about the other.

### Two live defects fixed here

- **The "adding another account" flag is a string tested for truthiness.** An explicit `false` therefore takes the add-more branch, and the stack's own parameter type claims the value is a boolean when it is not. It must be compared exactly, and the type must stop lying. MA-011 depends on this working — its whole add-another round trip runs through this flag.
- **The screen reloads the account list on mount** even though startup already loaded it and saving publishes its own refresh. The load goes.

### The post-save checkpoint

This is behaviour the mockup draws and no task owned. Frame A3's caption states it and C4/C6 are where a user meets it: **when the account insert succeeds but the step write fails, the retry repeats only the step write and never re-inserts the account.**

The failure the user sees is about the step, not the data. Their account is on disk. Tapping the primary action again must not produce a second account — and it must not be prevented from retrying either, because the step really does need writing. The error renders in the shell's status track, which MA-004 delivered; the form reports its failure and the host renders it.

This is the interaction between the guarded save path from MA-007 and the persist-before-navigate ordering from MA-005, and it is the single most valuable thing to force on the emulator in this task: make the step write fail with an account already inserted, tap retry, and count the rows.

**Behaviour that must be preserved exactly:** duplicate names still rejected case-insensitively after trimming; current balance still equals opening balance; credit-only values still absent rather than zero on non-credit accounts; and a successful save still advances to the more-accounts step, persisting before it navigates and replacing rather than pushing, per MA-005.

**Done when:** both entry points render from the same form, and the duplicated form body, submission mapping and colour list exist in exactly zero places; the add-more flag is compared exactly, its declared type matches what is actually passed, and a test covers the explicit-`false` case that is broken today; no onboarding route loads the account list itself; a forced step-write failure after a successful insert leaves exactly one account row, shows the error in the status track, and retries into the next step without inserting again; and creating an account from onboarding and from Settings on the emulator both produce a correct row, checked against the database.

# MA-012 — N4 Ready — the corrected starting net position

## Summary

Fix the first number MoneyApp ever shows a person, and rebuild the screen that shows it: seven states, one geometry, and a refusal to guess an exchange rate.

## Details

Reference frames are mockup F0 through F9. The formula, the sixteen-row test table and the seven display states are in `spec.md` § *Financial Logic — Starting net position*, which is the authority for this task and should be read before anything is planned.

**The number is wrong today.** The summary adds up account balances by summing them — it ignores currency entirely, so an Egyptian-pound account and a dollar account are added together as if they were the same thing, and a credit card's debt is added to net worth instead of subtracted from it. Anyone with a credit card or a foreign-currency account sees a wrong number as their very first impression of the app.

**What must be true instead:** credit-card accounts subtract and everything else adds; each account's opening balance converts into the base currency before it is counted; conversion is not symmetric, so which side is dollars decides whether the rate multiplies or divides; each converted value is rounded before the sum and the sum is rounded once more; archived accounts are excluded; and credit limits, minimum payments and carried debt are metadata that never enter the number.

**When conversion is needed and no verified rate exists, the app shows no number at all.** It says a rate is needed and points at the dashboard. It does not substitute the stored fallback, does not use zero, does not show a partial total, and does not add unlike currencies. The stored rate carries a marker for whether it was ever actually set; an unset rate is not a rate, and the value sitting in that slot before anyone sets one is an unverified guess that must never reach this screen. **This is the single most important row in the test table** and the reason the whole screen exists in this scope.

**Zero and negative are valid answers, not errors.** Neither is painted red. The number is gold in every state — the sign carries the fact, the caption carries the meaning, and the first number shown to someone who legitimately owns a credit card is not styled as a failure.

**Seven states, all drawn, all with copy that earns its space:** all-base-currency, mixed with a saved rate, mixed with no rate, negative, zero, a single account, and credit-card-only. The spec table maps each to its condition, its caption and its pills. Which state renders is a decision, not rendering, and it belongs in its own tested function beside the resolver. **Two things pluralise on the same count**, the account count and the words "opening balance" — getting that wrong is the "1 accounts" tell that makes a first-run screen feel unfinished.

### The approximation pill — read @layla's ruling before planning, it reverses the draft

The pill that restates the total in the other currency was drafted as "hidden when the base currency is dollars". **@layla overruled that while step 3 was running.** It renders in both base currencies; what changes is which currency it converts *into*, and the direction of the conversion with it. Hiding it was fixing the wrong half of the problem.

Both pills — the saved rate and the approximation — share one visibility gate: an amount was produced, and at least one account is in a currency other than the base. A saved rate that nothing needed earns no pill, in either base. The sign is never hidden or flattened; a pill that disagreed in sign with the number above it would be two facts, not one fact twice.

The rule, the four base-and-rate combinations, three worked examples including a negative, and a nine-row executable table are in `spec.md` § *Financial Logic — The approximation pill — ruled*. That section is the authority. Two of its rows exist specifically to catch regressions this task could plausibly introduce: the dollars-base row catches reverting to "hide it", and the zero row catches a falsy-zero check hiding a pill whose value is legitimately zero — the same footgun the main resolver already guards against.

**That flag is now decided — Marcus ruled, 2026-08-06.** The mockup draws the pill with no decimal places while every other amount on the screen carries two. **Use `formatCurrencyAmount`, two decimals, and let the `≈` carry the approximation.** The mockup's pixels are overruled here.

> ⚠️ **The ruling stands, but it does not fit the row as drawn. This is a planning input, not a detail.**
>
> Measured in a headless render of `assets/mockup.html` at its own 390pt reference, frame **F2**: the three pills need **329.1pt** of a **330pt** row. **0.9pt of headroom.** Widths are `3 accounts` 90.4 · `1 USD = 48.60 EGP` 137.4 · `2,169 USD` 89.3, gap 6.
>
> `.hero-pills` is `flex-wrap: wrap`, so `2,168.93 USD` does not clip — it **silently wraps to a second line**, taking the row from 22.5pt to roughly 50pt. That breaks two things: `spec.md` § *Composed height*'s 194pt card (the pill row is the `24` term), and **this task's own Done-when** — "the card is the same height in every state, asserted against the named geometry values" — which becomes unsatisfiable in F2, because there is no pill-row token to assert against.
>
> Marcus costed pill wrapping at *accessibility* text sizes (`mockup.html:2410`). Two decimals moves it to **base** size, which he did not cost.
>
> **The plan must resolve this explicitly and state which it chose.** Three options, none free:
> - **Reserve a two-line pill track** as a named geometry token. Honest and assertable, but ~28pt of dead space in the six states that never need it — the same trade Marcus rejected for the caption slot, for the same reason.
> - **Shorten the rate pill.** At 137.4pt it is the widest by 47pt; `48.60 EGP/USD` buys back roughly 40. Cheapest, and it keeps every state on one line.
> - **Drop the approximation pill in F2 only.** Contradicts @layla's rule that both pills share one gate — do not do this without her.
>
> This is geometry serving a display decision, so it is **@marcus's call at step 4**, with @layla consulted if the third option is on the table.

The reasoning matters more than the digits: rendering one pill through a second, shorter formatting path is how this app ended up with the same twelve colours declared in two files and the swatch row written three ways — duplication that `scope.md` names as a reason this scope exists. Opening a fresh instance of that to save two characters is a bad trade. One money-formatting path, everywhere, no exceptions.

@layla's computed value is unchanged; only the digit count was ever in question, and it is no longer open.

**One geometry holds all seven.** The value sits in a slot tall enough for the largest type size the design uses, and drops one size step when the formatted amount runs long rather than wrapping or reflowing the card. The caption slot is a fixed two lines and is never empty. Frame F0 is the proof: the same card, five value cases, identical height in all five. That claim is checkable from the named geometry values from MA-001 rather than eyeballed, and a test should check it.

**The number is deliberately larger than the equivalent number on the dashboard.** That is Marcus's call, it is reversible, and it is why the value slot grew. `spec.md` § *Product & UX — N4* records both the size and the consequence. The dashboard's own hero component is not imported here — this screen composes the same underlying shell the same way, and a dashboard component does not cross into onboarding for one screen's benefit.

**Three blocks rise in on mount**, staggered, once, opacity and a small lift only, and not at all under reduce-motion (`spec.md` § *Motion budget*). The only other motion on this screen is the spinner on the busy button.

**Finishing is the only place onboarding is marked complete**, per the business rules, after which the existing root layout performs the redirect. The button reads "Opening…" while it works, using the caller-supplied busy label MA-004 added. If completion fails, the screen stays, the summary is preserved — not blanked, not skeletoned, not recomputed — and the same button retries.

**No route-level loading.** The account snapshot and the rate are both owned by startup; this screen reads them and does not fetch them. The load this screen performs on mount today goes.

**Done when:** the resolver passes every row of the spec's table, including both conversion directions, the round-then-sum case, and the unverified-rate refusal; the state-selection function has its own tests for all seven states including both pluralisation points; every row of @layla's pill table passes, including the dollars-base row and the zero row; the pill's digit count is stated in the plan and matches what ships; all seven display states are reachable and correct on the emulator, with the mixed-no-rate state driven by clearing the saved rate and confirmed against what is actually in the database; the card is the same height in every state, asserted against the named geometry values; the three blocks animate once on mount and not at all with reduce-motion on; a forced completion failure preserves the summary and retries on the same button, matching F9; the mount-time load is gone; and completing the flow marks onboarding done exactly once and lands on the dashboard.

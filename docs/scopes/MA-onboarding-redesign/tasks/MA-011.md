# MA-011 — N3 Add more accounts

## Summary

Rebuild the third step: confirm the first account saved, list what exists in a stable row layout, and offer adding another without losing the persisted step.

## Details

Reference frames are mockup E1 through E5; the composition and copy are in `spec.md` § *Product & UX — N3*.

**The screen opens by confirming the save**, with a small success chip rather than a celebration block, then the same scale-led composition the first screen uses — ghost numeral, gold rule, left-aligned heading — and a line saying one account is enough.

**The account list is the subject of the screen** and reads that way because it is the only dense block on an otherwise spacious page, not because of any applied material. Rows reserve fixed columns for the colour dot, the name and type, and the amount and its currency. A long name truncates to one line rather than wrapping the row taller, and a formatted value never resizes a row. Each dot is a flat swatch of that account's own colour, so the list doubles as a colour key.

**Each row shows its balance in its own currency, and there is no running total.** A total needs an exchange rate, a rate may not exist, and deferring that to the final step keeps the conversion problem in exactly one place. This is settled, not a simplification to revisit.

**Two blocks rise in on mount**, staggered, once, opacity and a small lift only — the same treatment the first screen uses, and not at all when the user has reduced motion enabled (`spec.md` § *Motion budget*). Nothing else on this screen moves, and the list itself never animates on change.

**Adding another account** opens the account form in add-more mode **without changing the persisted step** — saving or cancelling both return here. That round trip runs entirely through the exact-comparison flag MA-008 fixed; if it misbehaves, the defect is there, not here. Continuing persists the final step before navigating and replaces the route, per MA-005's contract.

**The empty case is a guard, not a state.** A resumed session that lands here with zero accounts redirects to the account form before this screen can paint. That redirect is MA-005's resolver and is not re-implemented here; what this task owns is frame E3 — the honest dead end that renders if the resolver is ever wrong, because a broken success screen ("First account saved" above an empty list) is worse. E3 deliberately has no ghost numeral, no gold rule and no success chip: the celebratory composition belongs to the populated screen.

**There is no list skeleton, ever.** The account snapshot is already loaded before this route mounts and saving republishes it, so the list renders on first paint. The only loading state on this screen is the step transition. The reload this screen currently performs on every focus is removed — that is redundant work on a screen whose data is already owned elsewhere, and it is defect class 2 in `.claude/rules/review.md`.

**A failed step write preserves the list and the success chip.** The copy says so explicitly, because "couldn't save" next to a list of accounts otherwise reads as "I lost your accounts". The first account really was saved; the failure is about the step.

**Done when:** the screen matches E1 and E2 on the emulator with one account and with several; a thirty-two character account name truncates in place without changing the row height; the two blocks animate once on mount and not at all with reduce-motion on, watched with the setting toggled; adding another account and returning leaves the persisted step untouched, including when the add-more flag is passed explicitly false; a resumed session with zero accounts lands on the account form rather than here; a forced step-write failure leaves the list and chip intact with the error in the status track, matching E5; the focus reload is gone; and tests cover the add-more round trip and the persist-before-navigate ordering.

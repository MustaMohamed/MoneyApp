# MA-002 — Spike: gradient-filled headline, with the flat fallback

## Summary

Prove or disprove the gradient-filled `Finally clear.` headline on a real emulator, and ship whichever of the two treatments survives. Both have identical geometry, so nothing downstream changes either way.

## Details

The approved N1 headline fills the words `Finally clear.` with a three-stop gradient that holds gold through "Finally" and turns to teal on "clear." — mockup § B, frame B1, and the risk note that closes section B. **Nothing in this app does gradient-filled text today.** The user chose this treatment explicitly after comparing it side by side with the flat alternative, so it is the design; what is unresolved is whether it works.

This task is early and standalone by instruction. Nothing structural depends on its outcome, and N1 is not built until MA-010.

**Three things decide it, and all three are pass/fail:**

1. **It scales with the system font size** rather than rasterising at one fixed size. A headline that stays 42 px while everything around it grows is worse than no gradient.
2. **The accessibility label survives.** Gradient text is drawn as a vector, and a screen reader does not read a vector as text. Without an explicit label and an image role, the first screen a blind user meets is silent. This is not decoration to be added later — it is the acceptance condition.
3. **First paint does not regress.** This is the app's very first screen and the cold-start budget is under two seconds on mid-range Android. Measure it, do not assert it.

### The fallback is a decision this task makes, not one it defers

**Flat gold, same size, same position, same line break, same contrast pass, zero layout change.** It costs nothing and it is already known to work.

The rule is one attempt. Build the gradient treatment, run the three checks, and:

- **All three clean → ship the gradient.** Record the first-paint number in this file.
- **Any one of them short of clean → ship the flat fallback in this same task, on this same branch, and close the question.** Write down which check failed and what was observed. Do not open a second round, do not try a different drawing technique, do not carry it forward as "revisit later", and do not leave both treatments in the tree behind a flag. The scope does not wait on this and MA-010 must not inherit a choice.

Either way this task merges with exactly one headline treatment in the codebase and MA-010's plan does not branch. If the fallback ships, the outcome is reported to the user as an outcome, not as a blocker — the design was approved with this substitution named in `scope.md` § *Carried into the build*.

**Whichever treatment wins is delivered as a reusable headline element that N1 consumes in MA-010**, called the same way either way, so a reader of MA-010's plan cannot tell which one shipped without opening this file.

**Done when:** the emulator run has shown the headline rendering at the system's default font size and at a large accessibility size; the screen reader has been observed announcing the headline text; a first-paint measurement is recorded in this file with the number, not an adjective; exactly one treatment is committed, with a test covering its accessible name; and if it is the fallback, the specific observation that rejected the gradient is written here.

SVG `fontSize` is a raw user unit. **The component must multiply by `useWindowDimensions().fontScale` itself, or check 1 fails by construction.**

   **Doing that is the implementation of check 1, not a way around it.** The task's check 1 is "it scales with the system font size rather than rasterising at one fixed size"; a component that reads the OS font scale and redraws at the new size satisfies that literally. What *would* be working around it is capping or damping the scale, and *Detail step 7* already puts that out of bounds. **But the scaling it produces is linear in `fontScale`**, while every other string on N1 is an RN `Text` whose size Android applies natively — and on Android 14+ that path can be non-linear at large scales. So the real risk is not "doesn't grow", it is "grows differently from its neighbours", and check 1 below is amended to measure that rather than assume it away.
6. **The font trap, and it is the one that will silently ruin this.** `TSpanView.java:1127-1140` derives an Android `Typeface` style from `fontWeight`: `:1128` is `font.fontWeight == FontWeight.Bold || font.absoluteFontWeight >= 550` → `Typeface.BOLD` at `:1135`. It then tries `assets/fonts/<family>.otf|.ttf` (`:1146-1170`) — absent here, because `app.json:32` lists `expo-font` with **no options**, so no face is embedded — and falls through to `ReactFontManager.getInstance().getTypeface(fontFamily, style, assets)` (`:1177`). `expo-font` registers faces with `setTypeface(name, Typeface.NORMAL, tf)` (`node_modules/expo-font/android/src/main/java/expo/modules/font/FontLoaderModule.kt:59`), which fills only the **NORMAL** slot of that family's `AssetFontFamily` (`ReactFontManager.kt:106-110`). A lookup at style `BOLD` misses that slot, falls to `createAssetTypeface`, finds no `Sora_700Bold_bold.ttf`, and returns **Roboto**. The deprecated `com.facebook.react.views.text.ReactFontManager` that `TSpanView.java:42` imports is a thin delegate to the same singleton (`views/text/ReactFontManager.kt:22,55-59`), so that is not the problem — the style slot is. **Pass `fontFamily={FontFamily.soraBold}` and never pass `fontWeight`.** This is the same rule `.claude/rules/ui.md` already states for className fonts ("never pair a family class with a weight class"), arriving from the other direction.

   **Verified at plan review that omitting the prop is sufficient**, so the rule is not merely prudent — it is exactly right. `FontData.java:119-120` defaults `fontWeight = FontWeight.Normal` and `absoluteFontWeight = AbsoluteFontWeight.normal` (400), and `FontData.java:171-186` only overwrites them when the props map `hasKey("fontWeight")`. Passing `fontWeight={700}` — or the string `"bold"` — is what breaks it.

   **Where @dev will hit this rule:** it is repeated as a comment directly above the `<SvgText>` in *Detail step 4*, and its failure mode is a named, measured condition in *step 6*. Do not rely on reading this list.
7. **`letterSpacing` on SVG text is in user units, not em** — `TSpanView.java:296` divides by `fontSize * mScale` before calling `paint.setLetterSpacing` (which takes ems). The density cancels, and that is worth showing so nobody "fixes" it later: `FontData.java:227-229` multiplies the raw prop by `scale` (= `mScale` = display density, `VirtualView.java:39`) on the way in, so the value handed to `setLetterSpacing` is `(prop × density) / (fontSize_dp × density) = prop / fontSize_dp`. **So pass `fontSize × −0.01`, not `−0.01` and not `fontSize × density × −0.01`.**
8. **Accessibility props reach the native view.** `Svg.tsx:92-99` destructures only `style/opacity/viewBox/children/onLayout/preserveAspectRatio` and spreads the rest onto `RNSVGSvg` (`:191-194`); `fabric/AndroidSvgViewNativeComponent.ts:27,50` declares `ViewProps` (RN's, minus `pointerEvents`/`hitSlop` — `fabric/utils.ts:3`) plus an explicit `accessible`. /**
 * Geometry for the N1 display headline. Both treatments consume this, so the
 * gradient and the flat fallback occupy identical space — the spike can swap
 * one for the other without MA-010 noticing.
 *
 * Metrics read from node_modules/@expo-google-fonts/sora/700Bold/Sora_700Bold.ttf
 * (head/hhea/OS/2): unitsPerEm 1000 · ascent 970 · descent -290 · lineGap 0 ·
 * capHeight 730. An SVG viewport clips; a React Native line box does not, which
 * is why the drawing area is the full 1.26em glyph box and a negative top inset
 * pulls the element back to the 1.05 line box the mockup draws.
 */
const SORA_ASCENT_EM = 0.97;
const SORA_DESCENT_EM = 0.29;

/** Mockup § B, `.b-headline { line-height: 1.05 }`. */
export const DISPLAY_HEADLINE_LINE_HEIGHT = 1.05;
/** Mockup § B, `.b-headline { letter-spacing: -0.01em }`. */
export const DISPLAY_HEADLINE_TRACKING_EM = -0.01;

export interface DisplayHeadlineGeometry {
  /** Drawn size in dp, already multiplied by the OS font scale. */
  fontSize: number;
  /** SVG viewport height in dp — the full glyph box, so nothing is clipped. */
  boxHeight: number;
  /** Baseline offset from the top of the viewport, in dp. */
  baselineY: number;
  /** react-native-svg takes this in user units, not em (TSpanView.java:295). */
  letterSpacing: number;
  /** Negative margin that reduces the footprint to one 1.05 line box. */
  topInset: number;
}

export function resolveDisplayHeadlineGeometry(
  scaledFontSize: number,
  fontScale: number,
): DisplayHeadlineGeometry {
  const fontSize = scaledFontSize * fontScale;
  // boxHeight is derived FROM baselineY, never independently. Rounding the two
  // up separately makes (boxHeight - baselineY) a difference of two ceils, which
  // can land below fontSize * SORA_DESCENT_EM and clip the tail of "Finally" —
  // it does so at fontScale 0.85, 1, 1.15 and 2. Stacking the ceils makes the
  // descender space a ceil of the requirement, so it can only ever round up.
  const baselineY = Math.ceil(fontSize * SORA_ASCENT_EM);
  const boxHeight = baselineY + Math.ceil(fontSize * SORA_DESCENT_EM);
  return {
    fontSize,
    boxHeight,
    baselineY,
    letterSpacing: fontSize * DISPLAY_HEADLINE_TRACKING_EM,
    topInset: Math.round(fontSize * DISPLAY_HEADLINE_LINE_HEIGHT) - boxHeight,
  };
}

  container: {
    accessible: true;
    accessibilityRole: 'header';
    accessibilityLabel: string;
  };
  graphic: {
    importantForAccessibility: 'no-hide-descendants';
    accessibilityElementsHidden: true;
  };
}

/**
 * SVG text is drawn, not written — a screen reader reads a vector as nothing at
 * all. The wrapper carries the name (spec.md § Accessibility) and the drawing is
 * removed from the tree so the string is announced exactly once.
 *
 * The role is "header", not "image" (@marcus, 2026-08-06): it describes what the
 * element is to a user rather than how it happens to be drawn, it keeps the
 * announcement identical for the gradient and the flat treatment — which this
 * task requires — and it gives N1 a heading-navigation stop in MA-010. RN maps it
 * to isHeading on the node; "image" would have appended a spoken "image" after
 * the copy (ReactAccessibilityDelegate.kt:657-659 vs :674-676).
 */
export function resolveDisplayHeadlineA11y(text: string): DisplayHeadlineA11y {
  return {
    container: { accessible: true, accessibilityRole: 'header', accessibilityLabel: text },
    graphic: { importantForAccessibility: 'no-hide-descendants', accessibilityElementsHidden: true },
  };
}

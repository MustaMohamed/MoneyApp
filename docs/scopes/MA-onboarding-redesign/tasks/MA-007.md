# MA-007 — The shared account form, adopted by Settings

## Summary

Create the one account form the Accounts module owns, give it a real consumer immediately by replacing the Settings copy with it, and fix the amount parser that is silently corrupting opening balances.

## Details

Account creation exists twice and the two copies have already drifted. That duplication is a named reason this scope exists (`scope.md` § *Why now*). This task builds the single form and moves the first of the two entry points onto it. **MA-008 moves the second.** Splitting by consumer rather than by extract-then-adopt is deliberate: the form has a real consumer the moment it merges, so this is not a task that exists to make the next one compile, and the entry point on the live first-run path gets its own review sitting instead of riding inside a Settings refactor.

**This task is not the redesign.** When it merges, the Settings account form should look and behave as it does today, minus the parser defect below. The visual rebuild lands in MA-009, on the single surface this task creates.

**One form, one schema, one submission mapping.** The form owns the draft and its validation. It receives its presentation copy, its starting currency and what to do after a successful save from whoever is hosting it. **It knows nothing about routing, about the onboarding store, or about onboarding's step state.** That boundary is what stops the shared form from growing a mode per caller, and it is the contract onboarding depends on in MA-008.

**Plan it against both consumers, not just the one it lands with.** Onboarding needs a different starting currency, different copy, an add-more variant, and a host that persists a step after the save. None of that is built here, but a form shaped only around Settings will have to be reshaped in MA-008, and reshaping a shared surface twice is the outcome this split exists to avoid. `spec.md` § *Architecture — Module boundaries* states the contract; read it before planning.

### The parser defect — worse than the specification describes

`spec.md` § *Financial Logic — Account form* **used to say** the parser "accepts `5abc` → 5 and rejects `5,000` → NaN". The second half was wrong: `5,000` is not rejected, it persists as **5**. **That sentence was corrected in the spec on 2026-08-06**, so the spec and the table below now agree — plan against either. The table is kept here because it is the executable form. This has been run; it is not a reading of the code.

`5,000` is **not** rejected. It passes validation and persists as **5**. Because a new account's current balance is set equal to its opening balance (business rule 6), this is a silent thousandfold corruption of the first number a user types into MoneyApp, in both entry points, today.

Every one of these passes validation now and persists the wrong number:

| Typed | Persists today | Must, after this task |
|---|---|---|
| `5,000` | `5` | `5000` |
| `5,000.50` | `5` | `5000.50` |
| `5abc` | `5` | rejected |
| `5.5.5` | `5.5` | rejected |
| `0x10` | `0` | rejected |
| `1e3` | `1000` | rejected |
| `1_000` | `1` | rejected |
| `  7  ` | `7` | `7` — unchanged, both trim |
| `.5` | `0.5` | rejected — a deliberate behaviour change, leading digit now required |

Already rejected today and still rejected: empty, `abc`, `-3`, `Infinity`, non-ASCII digits.

The app already has a correct normalised decimal parser used elsewhere; the schema and the shared mapping both move onto it, and the mapping rounds with the shared monetary rule before persisting. **The schema and the mapping must use the same parser** — the present defect is exactly that they agree with each other while both being wrong, so a test that only checks one of them proves nothing. The parser reports "not a number" rather than returning one; the mapping must handle that rather than assert it away.

The same rule applies to every amount the form takes, not only the opening balance — credit limit, minimum payment and interest rate are parsed the same way.

**Two other things are fixed here because this is where they stop being duplicated:** the Settings entry point reloads the account list on mount even though startup already loaded it and saving publishes its own refresh, so that load goes; and the save path becomes a single guarded one — a second tap while a write is in flight is ignored, so one form session inserts at most one account.

**Behaviour that must be preserved exactly:** duplicate account names are still rejected case-insensitively after trimming; a new account's current balance still equals its opening balance; credit-only values are still stored as absent rather than zero on non-credit accounts; and the colour sheet from MA-006 still opens, stages and commits the same way.

**Done when:** the Settings entry point renders from the shared form and its own copy of the form, its own colour list and its own submission mapping are gone; every row of the table above is covered by a test against both the schema and the mapping; saving `5,000` from Settings on the emulator produces `5000` in the database, checked against the database and not against the screen; the redundant list load is gone; a double tap on save produces exactly one row; and the onboarding entry point still works exactly as it did, untouched.

const onValid = async (data: AddAccountFormData) => {

- Actions are read via `getState()` at call time, not captured at render. `.claude/rules/state.md`: reactive reads through the hook, actions through `getState()` outside render.

`saveErrorMessage` is used for **every** failure, including `AccountFormMappingError`. The user does not need to know which of two identically-shaped bugs fired; `console.error` carries the detail for `mqa logs`.

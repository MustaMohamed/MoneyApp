# MA-003 — Cross Fan logo: launcher, adaptive, splash, in-app mark

## Summary

Replace the Expo placeholder artwork with the approved Cross Fan mark on the launcher icon, the Android adaptive icon and the splash screen, and deliver the compact in-app mark the onboarding header uses.

## Details

The app still ships the Expo placeholder icon. The approved mark is the Cross Fan — three fanned account cards behind the folded MoneyApp symbol — with the teal accent dot **on the card corner, not over the stem**. That nudge is settled at gate 1 (`scope.md`, decision 3) and is not re-opened: dot-over-stem is the anatomy of a lowercase "i", and at launcher size the old placement read as "Mi".

Source artwork is in this scope's `assets/` folder: a vector master for lossless generation and a verified 1024×1024 raster. Locked construction — card angles, the diagonal midnight gradient, the thin warm border, the compact scale that must not be enlarged to fill the tile, and the rule that no text is embedded in the launcher mark — is in `assets/locked-design-2026-07-23.md` § *MoneyApp logo system*, which is functional detail and still current.

**Four surfaces:**

- **Launcher icon** — the full tile.
- **Android adaptive icon** — foreground only, with **all geometry inside the adaptive safe region**. Android crops the foreground to a circle or squircle depending on the launcher, and the fanned cards reach toward the tile corners. This is the one that goes wrong silently, and it goes wrong differently on different launchers.
- **Splash screen** — the same mark on the existing midnight background.
- **The in-app mark** — a compact element the onboarding welcome header renders beside the wordmark. It may drop non-essential detail at that size but must preserve card order, angles, colours and the folded mark. **MA-004 consumes it**, so it ships here even though nothing renders it yet in this task.

### The native-config rule this task must not break

**This is the only task in the scope that touches native configuration.** It replaces the files the existing configuration already points at; it adds no plugin, no dependency and no native source. That distinction is the whole reason it is not a critical trigger, and the plan must keep it true.

Concretely, and non-negotiably:

- **Nothing in this task adds, removes or reorders a configuration plugin.** Only asset files change.
- **Do not run the dependency-fixing Expo command.** It is known to re-add a date-picker plugin whose own require throws, which takes down `expo config`, every local dev build, and the prebuild CI job with an opaque module-not-found error. `CLAUDE.md` § *Expo Dev Client* and `spec.md` § *Risks* both name it. If a plan step believes it needs that command, that is a signal the task has grown past replacing artwork — stop and escalate rather than running it.
- **Diff the app configuration after every Expo CLI invocation of any kind**, including a plain prebuild, and attach the diff to this file. An empty diff is the expected result and is worth recording as such.

**A rebuild is unavoidable.** New launcher artwork does not appear from a reload — the emulator run needs a fresh install, and stale-icon caching on Android will lie to you.

**Done when:** the launcher icon, adaptive icon and splash all render the Cross Fan on a freshly installed build; the adaptive foreground has been checked under a circular mask with nothing important clipped; the compact in-app mark exists and is covered by a test for its accessible name; the app-configuration diff is recorded in this file and shows only the intended change with no added or reordered plugin; and the full CI-parity chain including the Android prebuild step is green.

### Verified facts this plan rests on

Every number below was measured in this session against the files on disk, not recalled. `@plan-reviewer`: facts 1–5 are the load-bearing ones.

1. **`@expo/prebuild-config@57.0.10` maps the adaptive foreground 1:1 onto the 108 dp canvas.** `pbc/build/plugins/icons/withAndroidIcons.js:364` computes `iconSizePx = (isAdaptive ? ADAPTIVE_BASELINE_PIXEL_SIZE : LEGACY_BASELINE_PIXEL_SIZE) * scale` with `ADAPTIVE_BASELINE_PIXEL_SIZE = 108` (`:74`) and `resizeMode: 'cover'` (`:372`); `configureAdaptiveIconAsync` (`:206-224`) passes `backgroundColor: 'transparent'` and `isAdaptive: true`. A square 1024 source becomes a square `108 × scale` foreground with **no padding and no inset added by Expo**. Therefore the Android safe zone is measured on *our source PNG* at these fractions of its width:
   - **mask circle** (the 72 dp viewport a circular launcher crops to, inside the 108 dp canvas): radius `W/3` = **341.33 px**;
   - **safe zone** (Google's recommended 66 dp diameter for key elements): radius `W × 33/108` = **312.89 px**.
2. **The iOS icon is composited onto white with transparency removed.** `withIosIcons.js:183-203`: `size = 1024`, `resizeMode: 'cover'`, `removeTransparency: appearance !== 'dark'`, `backgroundColor: '#ffffff'`. **`assets/icon.png` must therefore be fully opaque.** The verified raster is: measured `min alpha = 255` across all 1 048 576 pixels.
3. **The Android legacy and round icons come from `icon`, not from the adaptive foreground.** `withAndroidIcons.js:154` (`legacyIcon = icon ?? foregroundImage`), `:162` `generateRoundIconAsync(… borderRadiusRatio: 0.5 …)`. So `ic_launcher_round.webp` is a **circular crop of the full tile at radius 512 px**. The tile's ink reaches 723 px into the corners (it is edge-to-edge opaque), but everything the corners hold is the `#050B11` outer canvas and the outermost sweep of the rounded-rect corner; the cards' own ink stops at 310.8 px. Nothing of the mark is lost. No action needed — recorded so it is not later mistaken for a defect.
4. **`imageWidth: 100` is the *correct* value for the Android 12 splash, and raising it toward Expo's default of 200 would clip.** Read from `expo-splash-screen@57.0.5/plugin/build/withAndroidSplashImages.js:100-124`: `size = imageWidth * multiplier`, `canvasSize = 288 * multiplier`, the image is `contain`-fit into `size` and composited at `(canvasSize - size)/2`. `withAndroidSplashStyles.js` sets `windowSplashScreenBackground`, `windowSplashScreenAnimatedIcon`, `postSplashScreenTheme` and `android:windowSplashScreenBehavior` — and **no `windowSplashScreenIconBackgroundColor`**, which puts us on Android's *icon-without-background* spec: a 288 dp asset whose visible area is a **192 dp circle**, radius 96 dp. Our image occupies a centred 100 dp square; its half-diagonal is `100 × √2 / 2 = 70.71 dp ≤ 96 dp`, with 25 dp to spare, **whatever the artwork is**. The clipping threshold is `imageWidth = 2 × 96 / √2 = 135.76 dp`. Expo's default 200 would put the corners at 141 dp and clip them. `__tests__/app_config_plugins.test.ts` pins `imageWidth ≤ 135`.
5. **`assets/splash.png` is a 1 × 1 fully transparent PNG, 68 bytes.** The splash has never rendered anything but `#0F1923`. This task gives it artwork for the first time; it is not a replacement.
6. **The master SVG's three card gradients are inert, and the cards render flat.** `moneyapp-logo-cross-fan.svg` declares `<linearGradient id="back-card" x1="28" y1="18" x2="100" y2="69">` etc. with **no `gradientUnits`**, so they default to `objectBoundingBox` while carrying user-space coordinates — x1 = 2800 % of the bbox. Every shape lies entirely before stop 0, so each card paints its stop-0 colour flat. Sampled from the committed verified raster: front card `#E8C878` at both x = 320 and x = 680 on y = 700; middle card `#63B6F0` at both. Only `#background` (which *does* carry `gradientUnits="userSpaceOnUse"`) is a real gradient, so the locked "diagonal Cairo Nights gradient" on the **tile** is intact. **Do not fix this** — it is what gate 1 approved and what the verified raster shows. Open question 2.

### Step 4 — generate the two rasters, copy the third

```bash
cd "$S" && cat > render-icons.mjs <<'EOF'
import { Resvg } from '@resvg/resvg-js';
import fs from 'node:fs';
const REPO = '/home/user/MoneyApp';
const SRC = `${REPO}/docs/scopes/MA-onboarding-redesign/assets`;
const jobs = [
  ['moneyapp-logo-cross-fan-adaptive.svg', `${REPO}/assets/adaptive-icon.png`],
  ['moneyapp-logo-cross-fan-splash.svg', `${REPO}/assets/splash.png`],
];
for (const [svg, out] of jobs) {
  const r = new Resvg(fs.readFileSync(`${SRC}/${svg}`, 'utf8'), {
    fitTo: { mode: 'width', value: 1024 },
    background: 'rgba(0,0,0,0)',
  });
  const img = r.render();
  fs.writeFileSync(out, img.asPng());
  const { pixels: px, width: W, height: H } = img;
```

### Step 5 — the PNG decoder

- [ ] `src/test_helpers/png.ts`. Node built-ins only. It deliberately **throws** on anything but 8-bit RGBA non-interlaced rather than guessing, so a future asset saved in a different format fails loudly instead of silently asserting on garbage:

```ts
import zlib from 'node:zlib';

export interface DecodedPng {
  width: number;
  height: number;
  /** RGBA, 4 bytes per pixel, row-major. */
  data: Buffer;
}

/**
 * Minimal PNG decoder for asset tests. Supports the only format this repo's
 * committed PNGs use: 8-bit, colour type 6 (RGBA), non-interlaced. Anything
 * else throws — a wrong-format asset must fail the suite, not slip through as
 * misread bytes. No dependency: `zlib` is a Node built-in.
 */
export function decodePng(buf: Buffer): DecodedPng {
  if (buf.readUInt32BE(0) !== 0x89504e47) throw new Error('not a PNG');
  let off = 8;
  let width = 0, height = 0, depth = 0, colorType = 0, interlace = 0;
  const idat: Buffer[] = [];
  while (off < buf.length) {
    const len = buf.readUInt32BE(off);
    const type = buf.toString('ascii', off + 4, off + 8);
    const data = buf.subarray(off + 8, off + 8 + len);
    if (type === 'IHDR') {
      width = data.readUInt32BE(0);
      height = data.readUInt32BE(4);
      depth = data[8];
      colorType = data[9];
      interlace = data[12];
    } else if (type === 'IDAT') idat.push(data);
    else if (type === 'IEND') break;
    off += 12 + len;
  }
  if (depth !== 8 || colorType !== 6 || interlace !== 0) {
    throw new Error(`unsupported PNG: depth=${depth} colorType=${colorType} interlace=${interlace}`);
  }
  const raw = zlib.inflateSync(Buffer.concat(idat));
  const bpp = 4;
  const stride = width * bpp;
  const out = Buffer.alloc(height * stride);
  let p = 0;
  for (let y = 0; y < height; y++) {
    const filter = raw[p++];
    const line = raw.subarray(p, p + stride);
    p += stride;
    const cur = out.subarray(y * stride, (y + 1) * stride);
    const prev = y ? out.subarray((y - 1) * stride, y * stride) : null;
    for (let x = 0; x < stride; x++) {
      const a = x >= bpp ? cur[x - bpp] : 0;
      const b = prev ? prev[x] : 0;
      const c = x >= bpp && prev ? prev[x - bpp] : 0;
      const v = line[x];
      let r: number;
      switch (filter) {
        case 0: r = v; break;
        case 1: r = v + a; break;
        case 2: r = v + b; break;
        case 3: r = v + ((a + b) >> 1); break;
        case 4: {
          const pp = a + b - c;
          const pa = Math.abs(pp - a), pb = Math.abs(pp - b), pc = Math.abs(pp - c);
          r = v + (pa <= pb && pa <= pc ? a : pb <= pc ? b : c);
          break;
        }
        default: throw new Error(`bad PNG filter ${filter}`);
      }
      cur[x] = r & 0xff;
    }
  }
  return { width, height, data: out };
}
```

```ts
/**
 * The Android adaptive icon has no unit test anywhere else and its failure mode
 * is silent and launcher-dependent: a circular mask crops the foreground and
 * nobody sees it until a user with the wrong launcher does. @expo/prebuild-config
 * maps the source 1:1 onto Android's 108dp canvas
 * (withAndroidIcons.js:364, ADAPTIVE_BASELINE_PIXEL_SIZE = 108, resizeMode 'cover'),
 * so the two documented radii are exact fractions of this file's own width.
 */
const ALPHA = 8; // ink threshold; below this is antialias tail, not artwork
const MASK_FRACTION = 1 / 3; // 72dp mask circle within the 108dp canvas
const SAFE_FRACTION = 33 / 108; // Google's 66dp "key elements" safe circle

const asset = (name: string) => path.join(__dirname, '..', 'assets', name);
const read = (name: string) => decodePng(fs.readFileSync(asset(name)));

function ink(img: DecodedPng) {
  const { width: W, height: H, data } = img;
  let x0 = W, y0 = H, x1 = -1, y1 = -1, count = 0, rmax = 0;
  for (let y = 0; y < H; y++) {
    for (let x = 0; x < W; x++) {
      if (data[(y * W + x) * 4 + 3] <= ALPHA) continue;
      count++;
      if (x < x0) x0 = x;
      if (x > x1) x1 = x;
      if (y < y0) y0 = y;
      if (y > y1) y1 = y;
      const d = Math.hypot(x + 0.5 - W / 2, y + 0.5 - H / 2);
      if (d > rmax) rmax = d;
    }
  }
  return { count, x0, y0, x1, y1, rmax, cx: (x0 + x1 + 1) / 2, cy: (y0 + y1 + 1) / 2 };

  let m = 255;
  for (let i = 3; i < data.length; i += 4) if (data[i] < m) m = data[i];
```

### What the emulator run must show — and why it cannot run here

Stated in the house shape so `@impl-reviewer` at step 7 does not go looking for a run that does not exist, and so gate 3 inherits an explicit checklist instead of "look at the icon".

**Not executable in this container.** No `adb`, no Android SDK, no emulator, no Gradle. See the environment blocker above. What follows is therefore split into what step 7 *can* reproduce and what gate 3 *must* walk.

**Reproducible at step 7, deterministically, no device:**

1. `npm test -- app_icon_assets` — green. Then **prove the suite bites**: `git stash` the new `assets/adaptive-icon.png`, restore the placeholder, re-run, watch the mask and safe-zone cases fail with a ~723 px radius, restore. A geometry test nobody has seen fail is a geometry test nobody should trust.
2. `npm test -- app_config_plugins` — green, and bites: append a plugin to `app.json`, re-run, two failures, `git checkout -- app.json`.
3. `npm test -- logo_mark_a11y` — green, three cases.
4. `npx expo prebuild --no-install --platform android`, then `git diff --exit-code app.json` → exit 0, and the generated-resource listing from step 11 matches what is recorded here.
5. Decode `android/app/src/main/res/drawable-xxxhdpi/splashscreen_logo.png` and confirm ink radius ≈ 221 px in a 1152 px canvas. **This is the closest thing to a render check available**, and it is the one that would have caught the 1 × 1 placeholder.

**Deferred to gate 3 device QA, and the user should be told these are the unverified ones:**

- The launcher icon on a **freshly installed** build — Android caches launcher icons aggressively and a reinstall over the old package can keep showing the placeholder. Uninstall first.
- The adaptive icon under at least **two mask shapes** — a circular launcher and a squircle/rounded-square one. The pixel test proves nothing is *outside* the mask; only a device shows whether the mark reads well *inside* it, and whether the flat `#0F1923` background layer (which loses the tile's diagonal gradient and gold hairline — see open question 1) looks right next to other icons.
- The **splash**, which has never rendered anything. Check the mark's size on screen: it draws at `imageWidth: 100` dp with the artwork filling 88 % of that box, so ~88 dp. If it reads small, `imageWidth` is a one-number change up to 135 (fact 4 fixes the ceiling) and is a follow-up, not a rework.
- `LogoMark` on the dev primitives screen at `/primitives` — card order, the +8/−8/+1.5 angles, and the teal dot **on the card corner, not over the stem** (scope.md decision 3).
- TalkBack on the labelled catalog entry: "MoneyApp logo, image", once, not twice.

**The `mqa db` query that settles whether the write landed:** none, honestly — **this task writes nothing to SQLite**, adds no column, no repository call, no store field. ### Open questions

1. **The drop shadow is dropped from both derived artworks — @marcus should see this at gate 3.** `feDropShadow dy=3 stdDeviation=3.5` inside a `scale(5.7)` group has no analytically bounded extent, and the safe-zone assertion has to be an exact statement about ink. `locked-design-2026-07-23.md:128` permits derived compact variants to drop nonessential shadow detail, so this is inside the locked construction rather than a departure from it. The visible cost is on the adaptive icon: the rear midnight card `#344A67` meets the `#0F1923` background layer with no separating shadow. **Decided rather than deferred** — reversing it means re-deriving the safe-zone number against an alpha ramp, which is a worse test, so it should only be reopened if the device render is actually bad.
2. **The master SVG has two defects that gate 1 approved, and this task ships both unchanged.** (a) The three card gradients declare user-space coordinates with the default `objectBoundingBox` units, so every card paints flat at its stop-0 colour — sampled and confirmed identical at both edges of the front and middle cards. (b) The teal accent is `#4DBB93`, which is not in `theme_tokens.ts`, against `locked-design-2026-07-23.md:116` ("Cairo Nights runtime colors come from existing theme-token values"). Both are in the verified raster the design was signed off on. **Not fixed here** — silently changing approved artwork inside an implementation task is the wrong shape. If @marcus wants either corrected it is a new task against the master, and every derived file regenerates from the same two SVGs.
3. **The compact mark and the launcher tile are different drawings.** The tile fans three *differently sized landscape* cards; the mockup's `#mark` fans three *identical portrait* cards in flat token colours. Order, angles and the folded symbol match, which is what `locked-design-2026-07-23.md:126-129` requires — but side by side they are visibly not the same shape. This plan follows the **mockup**, because the mockup is what gate 1 approved and it is what MA-004 renders. Raised so @marcus decides deliberately rather than discovering it on the N1 header.
4. **`locked-design-2026-07-23.md:123` cites `moneyapp-logo-cross-fan-gradient-v2.png` as "the approved visual QA reference". That file does not exist** in `docs/scopes/MA-onboarding-redesign/assets/`. Not blocking — the master SVG and the verified raster are both present and agree with each other to 0.095 % of channels — but the locked design points at a QA reference nobody can open, and gate 3 would have used it.
5. **Android 13 themed (monochrome) icons stay unsupported.** `android.adaptiveIcon.monochromeImage` is unset, so a themed-icon launcher falls back. Adding it is an `app.json` *key addition*, and this task's entire licence to touch native config is that it adds nothing. Its own task if wanted.
6. **`verify: emulator` cannot be honoured — @sarah's call, recorded above rather than silently downgraded.** The frontmatter is left as-is on purpose.

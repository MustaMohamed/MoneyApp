# MA-006 — 32-colour bottom sheet replaces the swatch rows

## Summary

Build the colour picker the design specifies — thirty-two colours, all visible at once in a bottom sheet — and adopt it in the two Accounts-module screens where an account colour is chosen today.

## Details

An account colour is currently picked from a cramped wrapping row of twelve circles, written three different ways across the app. The approved replacement is a single sheet showing all thirty-two colours at once, as a chart: eight columns, two rows per tone block, with **column position meaning the same family in both blocks** — the rich and soft tones of one family sit directly above and below each other. Reference frames are mockup D1 and D2; the sheet's anatomy, labels and copy are in `spec.md` § *Product & UX — The 32-colour sheet*.

**Nothing scrolls.** Fitting all thirty-two on one fixed-size surface is the point: the picker reads as a complete chart rather than a list you have to hunt through.

**Selecting a colour must not move anything.** The selected cell gains a ring and a check mark, both drawn inside padding the cell always has, so no tile resizes and the grid never reflows. The check mark's colour is chosen per swatch so it stays legible on that specific colour — light swatches get a dark tick. Assuming white is the defect frame D2 exists to demonstrate. Both the tick colour and the family name come from the palette MA-001 published; nothing here re-derives either.

**Opening the sheet stages a choice; only the sheet's own confirm button commits it.** Closing by the close control or by swiping down discards the staged colour and leaves the form's value untouched. This matters because the sheet is opened from inside a form and a discarded pick must not dirty the draft.

**Each swatch announces its family and tone**, and whether it is selected. Colour is never the only signal.

**The row that opens it** shows the currently chosen colour, its family and tone in words, and a chevron — mockup C1's *Account colour* row. The words come from looking the stored value up in the palette, so a colour saved before this scope still names itself correctly.

**Scope of adoption in this task: the Accounts module only** — the add-account screen reached from Settings, and the account detail screen, which today share one twelve-swatch component. That component has exactly these two consumers and goes away with them. The onboarding copy is left alone here; it is deleted in MA-008 when onboarding adopts the shared form, and reaching into onboarding now would spread one task across two modules. The categories colour picker is a different feature with a different palette and is not touched.

**The account detail screen has a second, quieter problem to fix while you are in it:** the colour it falls back to when an account has none is read from the divergent twelve-value list, not from the list it draws swatches from. The two happen to agree on that one entry today, which is why nobody noticed. The default and the choices must come from the same source once this lands.

**Two things to check while building rather than after:** the sheet's built-in close control is a small icon button and may not clear a 44-point target without help; and a scrollable inside a sheet has to come from the sheet's own library or it will not scroll at all. This sheet is not scrollable, but the surrounding form is.

**Done when:** all thirty-two colours are reachable and selectable from both Accounts-module entry points; selecting one changes only the ring and the tick, with no cell resizing or grid reflow; discarding leaves the previous colour intact and confirming persists the new one through a save, confirmed against what is actually in the database; a test asserts the grid's column ordering pairs each family's tones and that every swatch has a distinct accessible name; an account with no stored colour opens on a default that is in the palette; and the twelve-swatch component the two screens shared is gone rather than left behind.

### Detail

#### Step 0 — decisions made before any code, with the evidence

These are settled. Do not re-open them mid-implementation; if one turns out false on the emulator, stop and report rather than branching.

**0.1 The sheet is `fitContent`, not `size="md"`. This overrides `spec.md:87`.**

`Sheet`'s `size` presets are *percentages of screen height* (`src/components/ui/sheet.tsx:102-110`), but this sheet's content height is nearly **fixed** — the cell height floors at `TouchSize.min` (44) below the 390 pt reference, so the grid barely shrinks while screen height varies from 568 to 932. Composed height, measured against the real tokens:

| Screen | Composed content + handle + `SHEET_FOOTER_CLEARANCE` | `md` = 60 % of height | Verdict |
|---|---|---|---|
| 320 × 568 | ≈ 491 | 341 | clipped |
| 360 × 800 | ≈ 500 | 480 | clipped |
| 390 × 844 | ≈ 528 | 506 | clipped |
| 430 × 932 | ≈ 572 | 559 | clipped |

`md` clips at **every** supported size; the mockup's own sheet is drawn at `height:512px` (`mockup.html:1804`) against a 60 % snap that yields 506 on the reference device. No single percentage works either — 320 × 568 needs 87 %, which would leave ~200 pt of dead surface on a 390 pt phone.

`fitContent` sizes the sheet to `min(containerHeight, contentHeight + handleHeight)` (`node_modules/@gorhom/bottom-sheet/src/hooks/useAnimatedDetents.ts:79-82`). **The footer height is not in that sum** — which is exactly why `sheet.tsx:20-26,78-85` requires consumers passing `footer` to add `SHEET_FOOTER_CLEARANCE` as their own `paddingBottom`. Do that and the composition above is the real measured height, and "nothing scrolls" holds by construction rather than by an arithmetic that must survive every font scale.

Cost accepted: `SHEET_FOOTER_CLEARANCE` (`Size.ctaHeight + ms(72)` = 124 at scale 1) is ~35 pt more than the footer shell actually occupies, so there is visible slack between the last grid row and the CTA's hairline. That is true of every sheet in the app today and is not worth a second clearance constant.

**0.2 The swatch is `RadioGroup.Item`, and selection state is announced by the primitive.**

`spec.md:89` specifies the accessible name `Nile Teal, rich, selected`. `RadioGroup.Item` already sets `role="radio"` and `accessibilityState={{ checked }}` at `primitives/radio-group/radio-group.tsx:86-93`, and consumer props are spread at **line 94, i.e. *after* those**.

> **Corrected at plan review (round 1).** The original text read "the state cannot be removed without abandoning the primitive". That is backwards: because `{...props}` is spread last, a consumer *can* clobber `accessibilityState` — which is exactly why step 5 forbids passing it. The argument does not rest on the spread order at all; it rests on ownership. The primitive owns `checked`, and baking `, selected` into the label on top of it makes TalkBack announce selection twice.

**Resolution: the accessible name is `"Nile Teal, rich"`; `checked` carries selection.** The Done-when's "every swatch announces family, tone and selected state" is satisfied, and "distinct accessible name" is satisfied by the 32 family+tone pairs. Recorded as a deviation from `spec.md:89` for `@plan-reviewer` and `@marcus`.

`RadioGroup.Item` is verified to forward everything needed: the wrapper destructures only `children, value, isDisabled, isInvalid, variant, className` (`components/radio-group/radio-group.tsx:84-92`) and spreads `...restProps` into the primitive at line 183, which spreads it into a plain RN `Pressable` at `primitives/radio-group/radio-group.tsx:94`. No `hitSlop` is destructured anywhere on that path, so the doc's `hitSlop | number | 6` default is stale for 1.0.8 and an `Insets` object passes through with RN's own type.

**0.3 The close control already clears 44 — `spec.md:91`'s "may need `hitSlop`" is answered: no change needed.**

`Sheet` renders `BottomSheet.Close` without `asChild` (`sheet.tsx:334-338`) → `BottomSheetClose` (`heroui-native/src/components/bottom-sheet/bottom-sheet.tsx:266-278`) → `CloseButton`, which hard-codes `hitSlop={12}` at `close-button.tsx:28`, **before** `{...restProps}` at line 29.

> **Corrected at plan review (round 1) — the visual size was wrong, the conclusion was not.** `CloseButton` is `size="sm"` `isIconOnly`, and `.button__root--size-sm { height: calc(var(--spacing) * 10) }` is **40** (`button.css:43-48`) — but `CloseButton` passes its own `className` (`close-button.styles.ts:4-6` → `.close-button__root`), and that class **overrides the height to `calc(var(--spacing) * 8)` = 32** (`node_modules/heroui-native/src/styles/components/close-button.css:2`, registered via `styles/components/index.css:9`). With `.button__root--is-icon-only { aspect-ratio: 1 }` (`button.css:66-69`) the control is **32 × 32**, not 40 × 40. (`--spacing: 0.25rem` comes from Tailwind v4's own theme, `node_modules/tailwindcss/theme.css:325`, × 16 — the same derivation `spec.md:403-407` already ratified for `Input`'s 48.)
>
> 32 + 2 × 12 = **56 × 56 effective**, still comfortably past `TouchSize.min`. The decision stands: do not add `hitSlop` to the sheet header.

Also note the spread order cuts the other way from how it reads: `hitSlop` is declared *first*, so a consumer passing its own `hitSlop` would win. `sheet.tsx:334-338` passes only `testID`, `isDisabled` and `iconProps`, so the 12 survives today — but that is a property of this call site, not a guarantee from `CloseButton`. Measure the bounds with `mqa find` at step 8 and assert **≥ 44**, not a specific number.

**0.4 The horizontal 44 pt floor is not reachable below 390 pt, and that is a design constraint, not a defect to engineer around.**

Cell width is `(screenWidth − 2·Spacing.md − 7·Spacing.xxs) / 8`. Computed against the real `ms()` formula (`src/utils/responsive.ts:15-22`, scale clamped to `[0.85, 1.15]`):

| Width | scale | `Spacing.md` | `Spacing.xxs` | cell W | cell H | hitSlop X | effective |
|---|---|---|---|---|---|---|---|
| 320 | 0.8500 | 14 | 3 | 33.875 | 44 | 1 | **35.875** |
| 360 | 0.9231 | 15 | 4 | 37.750 | 44 | 2 | **41.750** |
| 375 | 0.9615 | 15 | 4 | 39.625 | 44 | 2 | **43.625** |
| 390 | 1.0000 | 16 | 4 | 41.250 | 44 | 2 | **45.250** |
| 412 | 1.0564 | 17 | 4 | 43.750 | 46 | 2 | 47.750 |
| 430 | 1.1026 | 18 | 4 | 45.750 | 49 | 2 | 49.750 |

390 pt reproduces the mockup's stated `41.25 × 44` and `45.25 × 44` exactly (`mockup.html:1952-1954`). The three widths `spec.md:411-416` already enumerates as supported (320/360/375) fall **2.4–8.1 pt short** of `TouchSize.min` horizontally. Eight columns, 32 swatches and no scrolling cannot all hold at 320 pt; the alternatives (6 columns, or a scrollable) each break the one thing this feature exists to do.

Accepted, with the floor that *is* met stated: every supported width clears **WCAG 2.2 SC 2.5.8 (24 × 24 AA)** by ≥ 9.8 pt, and the vertical dimension is ≥ 44 everywhere. `hitSlop X` is derived as `Math.floor(gap / 2)` so slop can never overlap the neighbouring cell (2 × 2 ≤ 4 at every scale, including jest's `Spacing.xxs = 5`).

**0.5 `3` and `2` are scale-invariant, so they are named constants, not `ms()` calls.**

`ms(3)` is 3 and `ms(2)` is 2 at both ends of the `[0.85, 1.15]` clamp (`Math.round(3 × 0.85) = 3`, `Math.round(3 × 1.15) = 3`). Writing them as `ms()` would be a literal wearing a token — the same reasoning `onboarding_shell.geometry.ts:26-32` already applied to `Size.hairline`. Name them `ACCOUNT_COLOR_CELL_PADDING = 3` and `ACCOUNT_COLOR_CELL_RING_WIDTH = 2`.

**0.6 Secondary copy uses `text-content-secondary`, never `text-muted`.**

`global.css:32-33` — `--content-secondary` is `#6B7F99`, `--muted` is `#4A5568`. `spec.md:120-122`: `--muted` is 2.36:1 and is **decorative only, never carries text**. Existing screens misuse `text-muted` for text (e.g. `accounts/.../add_account/index.tsx:172,225`); those are **not** fixed here — out of scope, and they belong to MA-009's redesign of the same file.

#### Defects

**D1 — a discarded colour can be committed to the form. `src/modules/accounts/components/account_form/account_color_sheet.tsx:50-55`.**

```ts
const staged = isOpen ? stagedColor : lastStagedRef.current;   // line 50

const handleConfirm = () => {
  if (staged !== undefined) onConfirm(staged);                 // line 53
  onOpenChange(false);
};
```

`staged` was introduced to keep the grid selected while the sheet animates out. It is a *display* value: after `close()` it deliberately survives the store being cleared. But `handleConfirm` commits from it, so during the dismiss animation the CTA writes a colour the user just discarded.

**Failing scenario, concretely.** On the Add-account screen the colour is `#1B2B4B` (Royal Midnight, rich).

1. Tap the trigger row → `open('accounts/add_account', '#1B2B4B')`.
2. Tap **Sand, soft** → `stage('#E0C99A')`; `lastStagedRef.current = '#E0C99A'`.
3. Swipe the sheet down (or tap ×) → `onOpenChange(false)` → `close()` → `stagedColor: undefined`, `openOwner: undefined`. `isOpen` is now `false`, so `staged` falls back to `lastStagedRef.current` = `'#E0C99A'`.
4. **While the sheet is still sliding off screen**, tap where **Use this colour** still is. The footer is live: gorhom's footer sits in the animating container with no `pointerEvents` gate, and heroui only early-returns the *Overlay* on `!isOpen` (`node_modules/heroui-native/src/components/bottom-sheet/bottom-sheet.tsx:181-183`) — `Content` and its footer stay mounted and touchable until the sheet is off screen.
5. `handleConfirm` fires with `staged === '#E0C99A'` → `onConfirm('#E0C99A')` → RHF `onChange`. The trigger row now reads `Sand · Soft` and `formState.isDirty` has moved, from a discard.

Before the flicker fix this was safe: `staged` was `stagedColor`, which `close()` had already set to `undefined`, and the `!== undefined` guard swallowed the tap. The guard is what the fix silently disarmed — and it is exactly the invariant the plan review had verified ("`onChange` is called from exactly one place, and `close()` touches only the store"). The window closes when the sheet reaches index −1 and is translated off screen, so the exposure is the dismiss animation, not longer.

**Smallest responsible fix** — commit from the store, render from the ref. Keep `staged` for display only and read the live value in the handler:

```ts
const handleConfirm = () => {
  if (stagedColor !== undefined) onConfirm(stagedColor);
  onOpenChange(false);
};
```

While the sheet is genuinely open `stagedColor === staged`, so the intended path is unchanged; after `close()` the guard is armed again. Two words, no restructuring, and the flicker fix keeps working because line 50 is untouched.

#### D1 — verified closed, and the synchronous-close claim verified separately per path

@dev's argument was that `account_color_field.tsx:75-77` calls `close()` synchronously inside `onOpenChange`, so `stagedColor` is already `undefined` before the footer can be tapped. I traced each of the three exits rather than taking the claim whole, because it is only true for two of them.

| Exit | Where `onOpenChange(false)` is raised | Timing |
|---|---|---|
| Close control (×) | `BottomSheetClose.onPress` → `onOpenChange(false)` before any animation starts (`node_modules/heroui-native/src/components/bottom-sheet/bottom-sheet.tsx:264-273`) | **synchronous at tap** |
| Overlay press | `Overlay.onPress` → `onOpenChange(!isOpen)` (`primitives/bottom-sheet/bottom-sheet.tsx:129-138`) | **synchronous at tap** |
| Swipe down (pan) | `useAnimatedReaction` on `progress`, fires `scheduleOnRN(closeBottomSheet)` only when `progress > 1.5 && !isDragging` (`helpers/internal/components/bottom-sheet-content-container.tsx:38-49`) | **deferred to mid-animation** |

`progress` for a pan close is `interpolate(animatedIndex, [0, -1], [1, 2])` (`helpers/internal/hooks/use-popup-bottom-sheet-content-animation.ts:46-58`, `isPanActivated` is latched true by the first drag), so `progress > 1.5` means `animatedIndex < -0.5` — roughly halfway through the dismiss travel. That does not reopen D1, and here is the arithmetic. Android's dismiss is `duration: 250` with `Easing.out(Easing.exp)` (`node_modules/@gorhom/bottom-sheet/src/constants.ts:68-84`), i.e. `1 − 2^(−10t)`, which reaches half the distance at `t = 0.1` — **≈ 25 ms** after release, plus the `scheduleOnRN` hop and the React commit, call it one to three frames. The pre-existing window is therefore ~25–60 ms, and it is reachable only by a second finger landing on a footer that is already sliding away from where it was.

More to the point: **that window is not something the flicker fix or this fix created.** Strip `lastStagedRef` entirely and go back to `staged === stagedColor` and the swipe path behaves identically, because the store is still populated for those same 25 ms. My round 1 sentence "Before the flicker fix this was safe: `staged` was `stagedColor`, which `close()` had already set to `undefined`" assumed `close()` fired at gesture release. It does not.

# MA-009 — Account form redesign: type grid, message rails, credit slot

## Summary

Rebuild the shared account form to the approved design — a five-tile type grid, a permanent message rail under every field, and a reserved credit-card slot — and apply the credit-card rules the design settles.

> ✅ **Unblocked.** The carried-debt question that held this task at step 3 was ruled on by @layla while this review was running — see the section below. Nothing in this task waits on anyone.

## Details

Reference frames are mockup C1 through C6; the field order, labels, helper copy and credit rules are in `spec.md` §§ *Product & UX — N2* and *Financial Logic — Account form*.

**The account type becomes a grid of five tiles**, three across, left-aligned, each with an icon and its full label. The chosen tile is unmistakably chosen — it takes the app's existing hero treatment while the other four stay flat — and selection changes fill and border, never border width, scale or grid position. Bank is chosen by default so the form is never in a "nothing picked" state. A tap produces one short spring; nothing loops, and nothing runs at all when the user has reduced motion enabled.

**Every field carries a permanent message rail.** When the field is clean the rail holds its helper line; when it is not, the same rail holds the error. Compare frames C1 and C2: two errors appear and not one row moves, because the space was already there carrying something useful. At large accessibility font sizes the rail is a minimum rather than a fixed height — long error copy grows into the scrolling content and is never clipped.

**Opening balance and currency share a row.** The balance field is wider; the currency control is compact. The mockup draws a compact dropdown; the app's existing currency control is a full-width two-segment control. `spec.md` § *Known design/codebase disagreements* item 3 permits either, at identical geometry — **but the plan has to say which and why, not substitute silently.**

**The credit-card slot is reserved whether or not it is used.** When the type is anything else, its place holds a single-line hint naming what would open there. When Credit Card is chosen, the real fields open **exactly where that hint was**, so the page does not grow under the user's thumb. This costs about sixty points permanently on four account types out of five and buys the thing the scope exists to fix; it is a settled team decision (`scope.md`).

**The balance field is relabelled, not replaced.** Choosing Credit Card changes its label to "Amount currently owed" and its helper line to say that zero means a paid-off card. Nothing above it shifts, because nothing was inserted.

**Inside the slot:** credit limit, minimum payment, due day, and a switch for interest tracking that reveals an interest-rate field below itself, inside the same block, so the block grows downward and the header, rail and button never move. The switch is the design system's own; the plain grey system switch that appears nowhere else in the app is deleted. There is no separate revolving-balance field — two "how much do you owe" boxes on a first-ever screen is a comprehension trap, and that is settled (`scope.md`).

**The credit rules are in the spec and must be enforced in validation, not in the screen:** the limit is required and greater than zero, but debt above the limit stays valid so an over-limit card can be represented; the minimum payment is optional and cannot exceed what is owed; blank optional amounts stay absent while an explicit zero stays zero; the due day is an optional day of the month; the interest rate is required only while interest tracking is on. Every amount here is parsed with the same normalised parser MA-007 introduced — the case table in that task applies to all of them.

### What is written to the carried-debt column at creation — ruled

The form stops asking for this value, so something has to be written without asking. **@layla has ruled: zero for credit cards, absent for every other type.** Both are literals — neither is derived from the opening balance, which was the outcome she explicitly rejected. Her full reasoning, four worked code paths and three executable test tables are in `spec.md` § *Financial Logic — `revolving_balance` at creation — ruled*, and that section is the authority; do not re-derive it.

Two things about that ruling matter to whoever plans this task:

- **It is not a behaviour change today.** Absent and zero behave identically on every path that currently exists — the paydown arithmetic collapses them before it uses them, and the guard that treats them differently is never reached during transaction creation. Zero was chosen because it keeps a corruption tripwire live on future edits and deletes at no present cost, not because anything is broken now.
- **Nothing in the transactions domain changes.** This task writes a value; it does not touch the guard, the policy, or any existing query. A plan that proposes editing the transactions domain has misread the ruling.

@tariq's original argument for absent-everywhere was anchored to the wrong line and step 3 flagged it independently; @layla's correction supersedes both. The test rows for creation are her Part A; her Parts B and C are confirmation tests over unmodified existing code and are worth writing here because this ruling depends on their behaviour.

**A field-level error and a save-level error must never fight for the same space** — frame C6 shows both on screen at once, one in its own rail and one in the footer's status track. The status track is the shell's, delivered in MA-004; the form reports its failure and the host renders it. The post-save checkpoint behind that save-level error is MA-008's and is not re-implemented here.

**The button says "Saving…" while it saves**, back is disabled during the write, and a second tap is ignored — the guarded save path is MA-007's and this task consumes it rather than rebuilding it.

**Both entry points get this**, because it is one shared form. Settings account creation changes appearance in this task, and that is intended: account creation should behave identically wherever it is reached. Its emulator walk and its gate-3 QA both leave onboarding.

**Done when:** every frame from C1 to C6 is reproducible on the emulator; triggering two validation errors moves nothing above them; the keyboard opening moves the header and rail not at all, per C3; switching to Credit Card and back leaves the draft intact and persists only the values that belong to the chosen type; the credit rules reject and accept exactly the cases the spec table lists, under unit test; every row of @layla's Part A creation table passes, and her Parts B and C pass unchanged against the existing transactions domain with no edit to it; a test asserts the message rail's reserved height against the named geometry value from MA-001; the plain system switch exists nowhere in the codebase; and the Settings entry point has been walked on the emulator, not only the onboarding one.

## Plan

### Summary

- **The form body is recomposed, not rewritten.** `use_account_form.hook.ts`, `account_form.state.ts` and `account_color_sheet*` are untouched — MA-007's guarded save and MA-006's colour sheet are consumed exactly as they stand; `account_color_field.tsx` gives up one line, its own field label (step 6). What changes is `account_form.tsx`'s children, the schema's credit rules, and two lines of the mapping.
- **Account type becomes a HeroUI `RadioGroup`** of five tiles laid out as explicit rows of three. The selected tile draws a gradient + corner glow behind its content; every tile is the same box with the same 1 pt border at every moment, so selection cannot move anything.
- **Every field gets a permanent message rail** — one new `field_message_rail.tsx`, `minHeight: Size.fieldMessageTrack`, carrying helper copy when clean and the error when not.
- **Opening balance and currency share a row.** The currency control ships as the existing `SegmentedTabs`-based `CurrencySelector` at a fixed compact width, **not** HeroUI `Select` — decision 1 below, with the cost stated.
- **The credit slot is one unconditional node** at a fixed position in the form's child order. It renders a dashed hint or the real block; nothing above it is conditional, which is what makes "opens exactly where the hint was" structural rather than visual.
- **The credit rules move into `createAddAccountSchema`'s `superRefine`**, every one of them gated on `selected_type === AccountType.CreditCard`, so a leftover credit draft can never block a Bank save.
- **`revolving_balance` becomes a literal in `toNewAccountInput`** — `0` for Credit Card, `null` otherwise. `legacyRevolving` and the `revolving_balance` form field are deleted. `interest_tracking` gains the `isCC` gate MA-007 deferred to this task. No file under `src/modules/transactions/` is edited.
- **Draft retention across a type switch is RHF's default**, made explicit and tested; the mapping already nulls off-type values.

### Decisions made before any code, with the evidence

**1. The currency control ships as `SegmentedTabs`, not HeroUI `Select`.** `spec.md:526` permits either at identical geometry and forbids a silent substitution. Choosing `SegmentedTabs`:

- `Select` has **zero adoption in this tree** — `grep -rn "Select" src/ --include="*.tsx"` returns only `SelectablePill`, `setSelectedSegment` and similar. Its popover measures a trigger and mounts through `Select.Portal` into the same app-root `PortalHost` (`src/app/_layout.tsx:18,90`) that `AccountColorSheet` already uses. Introducing an unmeasured portal-and-popover primitive on the app's first-run screen, inside a scroll view, next to an open-able bottom sheet, is the largest unforced risk available in this task.
- A dropdown costs a tap and a frame to reveal two values that both fit on screen. `CURRENCY_SEGMENTS` (`src/constants/currency.ts:14-17`) is already `[{EGP}, {USD}]` — labels are the codes themselves, which is exactly the mockup's compact content.
- The compact geometry is reachable **exactly**, through an existing prop rather than a className override. `SegmentedTabs` already accepts `segmentWidth?: number` and applies it through `style` (`src/components/ui/tabs.tsx:96,166-170`), and turns on `adjustsFontSizeToFit` whenever it is set (`tabs.tsx:198`), so `EGP`/`USD` cannot clip.

  This matters because **`Tabs.List` sets `align-self: flex-start`** (`node_modules/heroui-native/src/styles/components/tabs.css:7`), so the list hugs its content and does **not** stretch to its parent. That corrects MA-008 D7's recorded inference ("`w-full` is very likely a no-op … RN's default `alignItems: 'stretch'` already makes a width-less child fill it", `MA-008.md:127`) — it is not a no-op, and MA-008 was right not to add it speculatively. With `segmentWidth` set, hug-content becomes a computed constant instead of an unknown, and no `listClassName` override is needed at all.

  Composed list width `= 2 × segmentWidth + 4 + 6`: `.tabs__list` gap is `calc(var(--spacing) * 1)` = 4 (`tabs.css:10`) and `.tabs__list--variant-primary` padding is 3 per side (`tabs.css:14`), with `--spacing: 0.25rem` resolved by Uniwind as `value * 16` — the same derivation `spec.md:405-407` already ratified for `Input`'s 48. **Those 10 points are unscaled** — CSS px straight from HeroUI's stylesheet, never routed through `ms()` — which is why `CURRENCY_CELL_WIDTH` below adds a bare `10` and not `ms(10)`.

**Cost, stated:** C1/C3/C5/C6 draw a chevron dropdown and this ships two visible segments. That is a user-visible deviation from the mockup, of the same shape and size as recorded disagreements 1 (gradient CTA vs flat) and 6 (48 pt button in a 52 pt slot). `CurrencySelector` gains one optional prop; every other consumer is unchanged by omission — there is exactly one other consumer, `src/modules/currency/index.ts`'s re-export. If Marcus wants the dropdown it is separate work with a measured popover behind it.

**2. The rail's reserved height is `Size.fieldMessageTrack` (`src/constants/theme.ts:201`, `ms(20)`), applied as `minHeight`, never `height`.** The token is MA-001's and already locked by `__tests__/geometry_tokens.test.ts:20`. This task asserts the *component* binds to it, in `__tests__/account_form.geometry.test.ts`, against the exported style object the component itself spreads — not against a literal, and not against rendered source text (`.claude/rules/tests.md`, audit M35).

`minHeight` is what makes the rail a floor rather than a ceiling: one line of `FieldError` or `Description` is `--text-sm` at its own line-height (`field-error.css:6-7`, `description.css:2`) = 20 at base font scale, which is exactly the token at `responsiveScale` 1.0. Under a user's larger accessibility font the line grows past 20, `minHeight` yields, and the copy grows into the scroll viewport instead of clipping — `spec.md:45`. Under `ms()` scaling above 1.0 the token exceeds the line and the rail is exactly the token. Both directions are asserted.

**3. The credit slot's reserved space is one node, not two aligned ones.** `credit_card_slot.tsx` is rendered **unconditionally**, always as the same child of `account_form.tsx`, always in the same position; the `isCreditCard` branch lives *inside* it and swaps its content. Every sibling above it is unconditional and type-invariant in count: the balance field is relabelled, never replaced (`FormLabelText` swaps one string), and its label carries `numberOfLines={1}` so neither `Opening balance` nor `Amount currently owed` can rewrap and shift the origin. That is the structural guarantee — the slot's top edge is a function of nodes none of which depend on `selected_type`. The emulator walk turns it into a number by comparing `mqa find` bounds across the switch (S2 below), rather than eyeballing two screenshots.

The hint's own reserve is `CREDIT_SLOT_MIN_HEIGHT = Size.fieldHeight + Spacing.md` in the geometry module — **not** a sixth `Size` token; MA-001 owns `theme.ts` and this is a composition of two tokens it already shipped. 48 + 16 = 64 against the mockup's `44 + 16 = 60`; the +4 is @sarah's `Size.fieldHeight` ruling (`spec.md:401-420`) propagating, same as everywhere else in this scope.

**4. Draft retention across a type switch is RHF's `shouldUnregister: false` default, and it is already in force.** `useController`'s unmount effect gates on `control._options.shouldUnregister || shouldUnregister` (`node_modules/react-hook-form/dist/index.esm.mjs:514,528`); `useZodForm` (`src/utils/use_zod_form.hook.ts:19-29`) sets neither, and `useAccountForm` passes only `mode`, `reValidateMode`, `defaultValues` (`use_account_form.hook.ts:59-63`). So unmounting `CreditCardFields` leaves its values in `_formValues`, and switching back re-mounts `Controller`s onto values that were never dropped.

The half nobody gets for free is **"only values belonging to the chosen type persist"**, and it has two independent halves, both of which must be tested:
- *Persistence*: `toNewAccountInput` already writes `null` for every credit column when `!isCC` (`account_form.helpers.ts:88-92`) — **with one hole this task must close.** `interest_tracking` is written ungated (`account_form.helpers.ts:86`), so a retained credit draft persists `interest_tracking = 1` on a Bank account, against `spec.md:296` ("All credit-only fields on non-credit types … `interest_tracking` persists `0`"). MA-007 left this deliberately and named this task: `__tests__/account_form.helpers.test.ts:222-233` asserts the ungated write today, with the comment *"Widening the gate is MA-009's call, not this task's."* Draft retention is exactly what makes it reachable, so this task widens it — step 4.
- *Validation*: every credit rule must be gated on the type, or a stale `min_payment` of `9,000` left over from a credit draft makes a Bank account unsavable with an error under a field that is no longer on screen. This is the trap in this task and it is why S3's emulator walk exists.

**Skip, never clear.** The gate skips *validating* off-type values; it must not null them out of the RHF draft. Clearing them would satisfy the same rule and break the Done-when clause directly above it — a Credit Card → Bank → Credit Card round trip has to come back to the values the user typed. Skip-plus-map-to-`null` keeps both clauses; clear-on-switch keeps one and silently loses the other.

**5. Every credit rule in `spec.md:284-296` maps to a Zod rule in `createAddAccountSchema`'s `superRefine`.** Table in step 3.

**6. The plain grey system switch is already gone, and this plan keeps it gone.** Verified rather than assumed: `grep -rn "Switch" src/ __tests__/` returns exactly two usages, both `import { Switch } from 'heroui-native'` — `account_form/credit_card_fields.tsx:1,115` and `budget/.../spending_plan_allocations.tsx:1,29`.

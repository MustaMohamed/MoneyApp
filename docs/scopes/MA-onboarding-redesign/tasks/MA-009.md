# MA-009 — Account form redesign: type grid, message rails, credit slot

## Summary

Rebuild the shared account form to the approved design — a five-tile type grid, a permanent message rail under every field, and a reserved credit-card slot — and apply the credit-card rules the design settles.

> ✅ **Unblocked.** The carried-debt question that held this task at step 3 was ruled on by @layla while this review was running — see the section below. Nothing in this task waits on anyone.

## Details

Reference frames are mockup C1 through C6; the field order, labels, helper copy and credit rules are in `spec.md` §§ *Product & UX — N2* and *Financial Logic — Account form*.

**The account type becomes a grid of five tiles**, three across, left-aligned, each with an icon and its full label. The chosen tile is unmistakably chosen — it takes the app's existing hero treatment while the other four stay flat — and selection changes fill and border, never border width, scale or grid position. Bank is chosen by default so the form is never in a "nothing picked" state. A tap produces one short spring; nothing loops, and nothing runs at all when the user has reduced motion enabled.

**Every field carries a permanent message rail.** When the field is clean the rail holds its helper line; when it is not, the same rail holds the error. Compare frames C1 and C2: two errors appear and not one row moves, because the space was already there carrying something useful. At large accessibility font sizes the rail is a minimum rather than a fixed height — long error copy grows into the scrolling content and is never clipped.

**Opening balance and currency share a row.** The balance field is wider; the currency control is compact. The mockup draws a compact dropdown; the app's existing currency control is a full-width two-segment control. `spec.md` § *Known design/codebase disagreements* item 3 permits either, at identical geometry — **but the plan has to say which and why, not substitute silently.**

**The credit-card slot is reserved whether or not it is used.** When the type is anything else, its place holds a single-line hint naming what would open there. When Credit Card is chosen, the real fields open **exactly where that hint was**, so the page does not grow under the user's thumb. This costs about sixty points permanently on four account types out of five and buys the thing the scope exists to fix; it is a settled team decision (`scope.md`).

**The balance field is relabelled, not replaced.** Choosing Credit Card changes its label to "Amount currently owed" and its helper line to say that zero means a paid-off card. Nothing above it shifts, because nothing was inserted.

**Inside the slot:** credit limit, minimum payment, due day, and a switch for interest tracking that reveals an interest-rate field below itself, inside the same block, so the block grows downward and the header, rail and button never move. The switch is the design system's own; the plain grey system switch that appears nowhere else in the app is deleted. There is no separate revolving-balance field — two "how much do you owe" boxes on a first-ever screen is a comprehension trap, and that is settled (`scope.md`).

**The credit rules are in the spec and must be enforced in validation, not in the screen:** the limit is required and greater than zero, but debt above the limit stays valid so an over-limit card can be represented; the minimum payment is optional and cannot exceed what is owed; blank optional amounts stay absent while an explicit zero stays zero; the due day is an optional day of the month; the interest rate is required only while interest tracking is on. Every amount here is parsed with the same normalised parser MA-007 introduced — the case table in that task applies to all of them.

### What is written to the carried-debt column at creation — ruled

The form stops asking for this value, so something has to be written without asking. **@layla has ruled: zero for credit cards, absent for every other type.** Both are literals — neither is derived from the opening balance, which was the outcome she explicitly rejected. Her full reasoning, four worked code paths and three executable test tables are in `spec.md` § *Financial Logic — `revolving_balance` at creation — ruled*, and that section is the authority; do not re-derive it.

Two things about that ruling matter to whoever plans this task:

- **It is not a behaviour change today.** Absent and zero behave identically on every path that currently exists — the paydown arithmetic collapses them before it uses them, and the guard that treats them differently is never reached during transaction creation. Zero was chosen because it keeps a corruption tripwire live on future edits and deletes at no present cost, not because anything is broken now.
- **Nothing in the transactions domain changes.** This task writes a value; it does not touch the guard, the policy, or any existing query. A plan that proposes editing the transactions domain has misread the ruling.

@tariq's original argument for absent-everywhere was anchored to the wrong line and step 3 flagged it independently; @layla's correction supersedes both. The test rows for creation are her Part A; her Parts B and C are confirmation tests over unmodified existing code and are worth writing here because this ruling depends on their behaviour.

**A field-level error and a save-level error must never fight for the same space** — frame C6 shows both on screen at once, one in its own rail and one in the footer's status track. The status track is the shell's, delivered in MA-004; the form reports its failure and the host renders it. The post-save checkpoint behind that save-level error is MA-008's and is not re-implemented here.

**The button says "Saving…" while it saves**, back is disabled during the write, and a second tap is ignored — the guarded save path is MA-007's and this task consumes it rather than rebuilding it.

**Both entry points get this**, because it is one shared form. Settings account creation changes appearance in this task, and that is intended: account creation should behave identically wherever it is reached. Its emulator walk and its gate-3 QA both leave onboarding.

**Done when:** every frame from C1 to C6 is reproducible on the emulator; triggering two validation errors moves nothing above them; the keyboard opening moves the header and rail not at all, per C3; switching to Credit Card and back leaves the draft intact and persists only the values that belong to the chosen type; the credit rules reject and accept exactly the cases the spec table lists, under unit test; every row of @layla's Part A creation table passes, and her Parts B and C pass unchanged against the existing transactions domain with no edit to it; a test asserts the message rail's reserved height against the named geometry value from MA-001; the plain system switch exists nowhere in the codebase; and the Settings entry point has been walked on the emulator, not only the onboarding one.

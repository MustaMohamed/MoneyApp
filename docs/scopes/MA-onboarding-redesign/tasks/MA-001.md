# MA-001 — Colour families, geometry tokens, and the 32-colour palette

## Summary

Add the four missing colour families, name the five geometry numbers the zero-shift contract rests on, and publish one canonical 32-entry account palette that every later task reads from.

## Details

Nothing on screen changes. This task exists so that the eleven tasks after it have one place to read a colour and one place to read a size, and so that the zero-shift contract becomes a statement a unit test can check rather than something device QA has to eyeball.

**Sixteen colour families, each with a rich and a soft tone, must be available to the app as a single source.** Twelve exist today; four — Jade, Indigo, Coral, Graphite — do not. Their exact values are in `spec.md` § *Architecture — Colour tokens and the palette*, which takes them from `assets/locked-design-2026-07-23.md` and matches what the mockup renders. No stored data changes and no migration is involved: an account colour is a plain value.

**The palette must carry more than hex.** Every entry needs the family's display name, which tone it is, and the colour a check mark must be drawn in to stay legible on that specific swatch — mockup D2 shows a near-black tick on Sand soft and a bone-white one on Nile rich, and "assume white" is the defect that frame exists to prevent. A screen reader announcing a swatch says the family name and the tone, so the same source has to supply both. The palette also has to answer the reverse question — given a stored hex, what family and tone is it — because the colour trigger row and the more-accounts list both name a colour they were only given as a value.

**Two identical twelve-colour lists and one divergent one exist today.** `spec.md` names all three call sites. This task adds the canonical source; it does not yet delete the duplicates, because their consumers are rewritten in MA-006, MA-007 and MA-008. What it must not do is add a fourth. The divergent list also feeds the categories picker, which is out of scope and is not touched.

**Five geometry numbers become named values:** the message rail under every field, the summary value slot, the summary caption slot, the footer status track, and the standard field height. Values and rationale are in `spec.md` § *Architecture — Geometry tokens*. Marcus asked for four; the fifth is the field height, which is currently an unwritten coincidence between two unrelated constants and will drift the first time either moves.

**The token export script must emit the two token groups it currently skips** — the shared colour set and the account palette — so the next mockup does not have to re-declare them by hand and drift from the app. This is item 1 of the mockup's *Where I reached outside the token set*. The export is a build-time artefact; it has no runtime effect and no screen reads it.

**Two facts already checked, so nobody re-derives them at step 4:** all thirty-two hex values are distinct — the four new families collide with nothing that exists — and the current token test asserts a family count of exactly twelve, so that assertion has to move to sixteen. It cannot be left passing.

**Why this task alone does not open the emulator.** Every value it adds is consumed by nobody until the task after it. An emulator run here would install a build and show today's app unchanged; the tasks that render these values are all `verify: emulator` and each is where a wrong number becomes visible. The claim that nothing renders differently is therefore the one thing that has to be mechanically true rather than eyeballed — see the last bullet below.

**Done when:** a test asserts all thirty-two palette entries exist, are unique, and carry a family name, a tone and a tick colour, and that a stored hex resolves back to its family and tone; a test asserts each of the five geometry values; the token test's family-count assertion reads sixteen and the whole existing suite is green with no test deleted; the token export includes both previously missing groups; and **the diff contains no `.tsx` file at all** — that is what makes "no screen renders differently" checkable without a device.
